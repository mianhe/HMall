# 子产品业务梳理产出指南

面向子产品的产品与研发团队，梳理子产品及其相关服务的业务全貌。

---

## 一、核心概念与产出

### 核心概念

- **子产品**：对电商价值流的部分阶段负责。例如，交易子产品负责从用户需求转化为可履约的订单，直至订单履约完成。一个子产品通常包含多个服务，由它们协作完成子产品的价值交付。
- **服务**：提供子产品所需业务能力的独立单元。当前我们将一个服务视同一个 **Bounded Context（限界上下文，简称 BC）**，后文中"服务"与"BC"含义等同。

### 产出

子产品梳理的产出分为两个层级：

**子产品级产出**——描述子产品的整体结构与端到端流程：

1. **Context Map（上下文地图）**：子产品包含哪些服务？各自负责什么？彼此怎么协作？
2. **业务流程**：子产品支持哪些端到端的业务流程？这些流程通常以事件的形式表达。

**服务级产出**——描述每个服务（BC）的内部细节：

1. **领域模型**：服务内的核心业务概念、概念之间的关系，以及重要的业务规则
2. **业务流程**（可选，取决于服务本身是否是重流程）：服务与外部的协作方式与服务内展开的业务流程
3. **业务能力列表**：服务支撑的业务能力及具体 Feature 场景

---

## 二、价值流全景：共同的分析框架

在开始梳理之前，团队首先需要理解自己所在子产品覆盖了价值流的哪些阶段。将电商流程划分为若干阶段，有两个核心目的：

- **统一语言，明确界限**：为不同子产品之间建立共同词汇和清晰的边界。
- **避免组合爆炸**：阶段之间通过分界事件解耦，使得各段可以独立演进，而不会因为跨段流程的排列组合而失控。

我们将电商的端到端流程划分为以下阶段，以便于分析和协同：

```
Intention → Needs → Paid Order → Fulfillment → Service / Use
 (购物意图)  (明确需求)  (已支付订单)   (履约完成)    (服务与使用)
```

| 阶段 | 含义 | 典型场景 |
|------|------|---------|
| **Intention** | 用户有模糊的购物意图 | 广告引流、活动页浏览、搜索推荐 |
| **Needs** | 意图转化为明确的商品需求 | 进入详情页、加入购物车、选择规格 |
| **Paid Order** | 需求转化为已支付的订单 | 下单 + 支付完成 |
| **Fulfillment** | 已支付订单完成履约 | 发货签收、服务激活、安装调试 |
| **Service / Use** | 用户持续使用或接受服务 | 售后、维修、退换、续费 |

不同的子产品覆盖不同的阶段。例如：

- **导购子产品**：覆盖 Intention → Needs（引流与转化）
- **交易子产品**：覆盖 Needs → Paid Order → Fulfillment（下单、支付与履约）
- **售后子产品**：覆盖 Service / Use（售后服务与持续使用）

**梳理第一步**：基于产品价值流，明确自己子产品的边界和定位，这是后续所有梳理的起点。

## 三、子产品级产出

### 3.1 Context Map（上下文地图）

> 示例：[交易子产品 Context Map](examples/context-map.md)

#### 是什么

Context Map 回答"子产品包含哪些服务、各自负责什么、怎么协作"。

#### 产出内容

##### (a) 服务清单与职责

列出子产品内的所有服务（BC），明确每个服务的核心职责。

**产出格式**：

| 服务（BC） | 职责 |
|-----------|------|
| Catalog | 类目、商品(SPU)、规格维度、SKU、展示图、商品类型与服务绑定 |
| Order | 订单创建、取消、查询、事件驱动、状态流转 |
| ... | ... |

##### (b) 服务间的集成关系

明确服务之间的上下游关系和集成方式。核心要回答：

- **谁调用谁？**（方向）
- **用什么方式？**（同步 REST / 异步事件 / 前端编排）
- **传递什么？**（关键数据）

**产出格式**：

| 上游 | 下游 | 集成方式 | 说明 |
|------|------|----------|------|
| Catalog | Order | REST/同步 | Order 创建时拉取 SKU 与价格 |
| Payment | Order | Kafka 事件 | PaymentCompleted / Expired 通知 |
| Cart | Order | 前端编排 | 前端从 Cart 取选中项 → 调用 Order API |
| ... | ... | ... | ... |

##### (c) 全景图

用图形（推荐 Mermaid flowchart）展示所有服务及其关系的全貌，实线表示同步调用，虚线表示异步事件。

### 3.2 业务流程（事件驱动、分段式）

> 示例：[交易子产品业务流程](examples/business-flows.md)

#### 是什么

业务流程描述"从用户需求到最终完成"的端到端路径。采用**分段梳理** + **事件驱动**的方式，将复杂流程拆解为可独立理解、独立验证的段。

#### 如何分段

将价值流覆盖的范围按**关键转折点**切分为若干段。段与段之间通过一个**分界事件**连接——上一段的终点事件就是下一段的起点事件，两段解耦。

**分段原则**：

- 分界事件代表一个**不可逆的业务状态转变**（如"已支付"、"已签收"）
- 段内的服务组合相对稳定，段间的服务组合可以不同
- 两段可以独立验证、独立扩展

**示例（交易子产品）**：

```
Needs ──→ Paid Order ──→ Fulfillment
├── N2O（转化段）───┤├── O2F（履约段）──┤
```

| 段 | 范围 | 分界事件 | 涉及服务 |
|----|------|---------|---------|
| N2O | 用户明确需求 → 支付完成 | PaymentCompleted | Cart、Catalog、User、Order、Inventory、Payment |
| O2F | 已支付订单 → 履约完成 | OrderCompleted | Fulfillment、Order |

#### 每段的产出内容

##### (a) 用户旅程（事件前的阶段）

如果该段有前端用户交互，先梳理用户旅程——用户经历哪些步骤、每步需要什么数据、数据来自哪个服务。这部分没有领域事件，但有**数据依赖**。

**产出格式**：

| 步骤 | 做什么 | 数据依赖 | 来源服务 |
|------|--------|---------|---------|
| 商品详情页 | 展示 SPU/SKU 信息、规格选择 | SPU、SKU、SpecDimension | Catalog |
| 结账页 | 汇总待下单商品、选择地址 | 选中项、用户地址列表 | Cart、User |

##### (b) 事件流

事件流是业务流程的骨架。用领域事件串联各服务之间的协作：

- 🟧 **领域事件**：已经发生的业务事实（如 OrderCreated、PaymentCompleted）
- ⌘ **命令**：触发动作的指令（如 PlaceOrder）
- ⟳ **策略**：事件触发的自动反应（如 PaymentCompleted → 创建履约单）

**产出格式**：Mermaid flowchart，标注事件名、所属服务、主流程与补偿路径。

梳理时覆盖三条路径：

| 路径 | 说明 |
|------|------|
| **主流程（Happy Path）** | 一切顺利时的完整路径 |
| **补偿路径** | 异常或超时时的回滚/补偿 |
| **重试路径** | 可重试的失败场景 |

##### (c) 路径枚举

列举该段内所有可能的业务路径（变量维度的组合）。路径枚举是测试覆盖的依据。

**产出格式**：

| 编号 | 路径 | 描述 | 变量维度 |
|------|------|------|---------|
| N2O-1 | 直接购买实体 | 详情页 → 立即购买 → 结账 → 支付 | 入口=直接, 商品=实体 |
| N2O-2 | 购物车结算实体 | 详情页 → 加购 → 购物车 → 结算 → 支付 | 入口=购物车, 商品=实体 |

## 四、服务级产出

每个服务（BC）产出以下三份文档：

### 4.1 领域模型（Domain Model）

> 示例：[Catalog 领域模型](examples/catalog/domain-model.md) · [Fulfillment 领域模型](examples/fulfillment/domain-model.md)

描述该服务内的核心业务概念、概念之间的关系，以及重要的业务规则。

**产出内容**：

| 内容 | 说明 |
|------|------|
| 模型图 | 聚合根、实体、值对象的关系图 |
| 实体与属性表 | 每个实体/值对象的属性、类型、约束 |
| 状态流转 | 聚合根的状态机（状态图 + 转换表） |
| 领域事件 | 该服务发布的所有领域事件及其触发时机 |
| 不变式 | 核心业务规则约束 |

### 4.2 业务流程（Event Flow）——可选

> 示例：[Fulfillment 业务流程](examples/fulfillment/event-flow.md)（Catalog 为轻流程服务，无此产出）

描述该服务与外部的协作方式与服务内展开的业务流程。并非所有服务都需要此产出，仅当服务本身是重流程时才需要。

**产出内容**：

| 内容 | 说明 |
|------|------|
| 参与方 | 该服务的上游/下游服务及集成方式 |
| 主流程与补偿 | 文字描述 + 流程图 |
| 事件契约 | 发布/订阅的事件、Topic、消息体 |
| 同步调用契约 | REST API 调用、请求/响应格式 |

### 4.3 业务能力列表（Requirements / Feature List）

> 示例：[Catalog 业务能力列表](examples/catalog/requirements.md) · [Fulfillment 业务能力列表](examples/fulfillment/requirements.md)

列出该服务的所有业务能力，每个能力下的具体 Feature 场景。Feature 采用 Gherkin 风格描述——Given / When / Then，足以作为验收测试的依据。

**产出格式**：

```
## 1. 管理类目
- 1.1 创建根级类目时应成功并返回名称且无父类目
- 1.2 在已有类目下创建子类目时应成功并返回名称及父类目
- 1.3 请求根下所有类目时应返回类目列表
...

## 2. 管理商品
- 2.1 在叶子类目下创建商品时应成功并返回商品信息
...
```

### 三份文档的关系

```
业务能力列表（What）── 这个服务能做什么？有哪些场景？
    ↓ 支撑
领域模型（How）────── 用什么概念和规则来实现？
    ↓ 协作
业务流程（With Whom）─ 和谁协作？数据怎么流转？（可选）
```

## 五、示例：交易子产品（HMall）

以下以 HMall 的交易子产品为完整示例，展示各产出物的实际形态。

### 5.1 Context Map

**服务清单与职责**：

| 服务（BC） | 职责 |
|-----------|------|
| **Catalog** | 类目、商品(SPU)、规格维度、SKU、展示图、商品类型与服务绑定、镭雕图案库 |
| **User** | 用户注册、登录(JWT)、收货地址管理 |
| **Cart** | 购物车增删改查、结算预览 |
| **Order** | 订单创建、取消、查询、事件驱动状态流转（编排中心） |
| **Inventory** | 库存占用与释放 |
| **Payment** | 扣款、退款、支付超时检测 |
| **Pricing** | 算价、优惠 |
| **Fulfillment** | 拆单、配货、发货、配送、镭雕完成与事件通知 |
| **Activity** | 消费各服务事件，构建业务活动记录 |
| **BFF** | 前端统一 API 入口，按路径前缀代理到各服务 |

**集成关系（摘要）**：

| 上游 | 下游 | 方式 | 说明 |
|------|------|------|------|
| Catalog | Order | REST | Order 创建时拉取 SKU 与价格 |
| User | Order | REST | userId、收货地址 |
| Cart | Order | 前端编排 | 前端取选中项 → 调 Order API |
| Order | Inventory | REST/同步 | 占用/释放库存 |
| Order | Payment | REST/同步 | 创建支付单/退款 |
| Order | Fulfillment | REST/同步 | 创建/取消履约单 |
| Payment | Order | Kafka 事件 | PaymentCompleted / Expired |
| Fulfillment | Order | Kafka 事件 | Allocated / Shipped / Delivered |
| 各服务 | Activity | Kafka 事件 | 全量事件订阅 |

### 5.2 业务流程

**覆盖范围**：Needs → Paid Order → Fulfillment（价值流中间两段）

**分段**：

```
Needs ──→ Paid Order ──→ Fulfillment
├── N2O（转化段）───┤├── O2F（履约段）──┤
     分界: PaymentCompleted     分界: OrderCompleted
```

**N2O 事件流（主流程）**：

```
⌘ PlaceOrder → 同步占库存 → StockReserved → 同步创建支付单 → OrderCreated
  → 用户支付 → PaymentCompleted
```

**N2O 补偿路径**：支付超时 → PaymentExpired → 取消订单 → OrderCancelled → 释放库存 → StockReleased

**O2F 事件流（主流程）**：

```
PaymentCompleted → 创建履约单 → FulfillmentOrderCreated
  → 配货 → FulfillmentAllocated → 发货 → FulfillmentShipped
  → 签收 → FulfillmentDelivered → OrderCompleted
```

**路径枚举（N2O 摘要）**：

| 编号 | 路径 | 描述 |
|------|------|------|
| N2O-1 | 直接购买实体 | 详情页 → 立即购买 → 结账 → 支付 |
| N2O-2 | 购物车结算实体 | 详情页 → 加购 → 购物车 → 结算 → 支付 |
| N2O-3 | 直接购买实体+虚拟 | 详情页选服务 → 立即购买 → 结账 → 支付 |
| N2O-4 | 购物车结算实体+虚拟 | 详情页选服务 → 加购 → 购物车 → 结算 → 支付 |

### 5.3 服务级产出（摘要）

以 Order 服务为例：

| # | 业务能力 | Feature 数 |
|---|---------|-----------|
| 1 | 创建订单 | 9 个场景（含参数校验、库存联动、服务类商品处理） |
| 2 | 取消订单 | 7 个场景（含状态限制、补偿链路） |
| 3 | 查询订单 | 3 个场景 |
| 4 | 事件驱动 | 7 个场景（订阅 Payment/Fulfillment 事件推进状态） |
| 5 | 补购服务 | 7 个场景 |

每个业务能力的详细 Feature 场景、领域模型、业务流程分别记录在服务级文档中。

## 六、产出物清单（Checklist）

梳理结束后，检查以下产出物是否齐全：

### 子产品级产出

- [ ] 价值流覆盖范围与分段定义
- [ ] Context Map：服务清单与职责表
- [ ] Context Map：集成关系表
- [ ] Context Map：全景图（Mermaid / 白板照片）
- [ ] 业务流程：每段的事件流图（主流程 + 补偿）
- [ ] 业务流程：路径枚举表
- [ ] 事件总表：所有跨服务领域事件汇总

### 服务级产出

每个服务（BC）应补齐以下文档：

- [ ] 领域模型：聚合、实体、值对象、状态机、不变式
- [ ] 业务流程（可选）：参与方、流程图、事件契约、同步调用契约
- [ ] 业务能力列表：业务能力分组 + 具体 Feature 场景
