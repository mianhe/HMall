# 本体（Ontology）

## 什么是本体

本体是对一个业务领域的完整形式化描述，回答三个根本问题：**领域中存在什么、会发生什么、能做什么。**

本体描述的是领域的真相，而不是系统的设计选择。判断一条陈述是否属于本体的标准：**换一套技术栈重写系统，这条陈述是否仍然成立。**

- "订单包含订单行项" → 成立 → 属于本体
- "OrderCreated 事件之后触发 StockReserved" → 成立 → 属于本体
- "订单在未支付前可以被取消" → 成立 → 属于本体
- "取消操作通过 `order_query(action='cancel')` 调用" → 不成立（技术方案） → 不属于本体

---

## 三个维度

本体由三个不可或缺的维度构成：

### 语义（Semantic）—— 存在什么

定义领域中的概念、属性、关系和约束。这是本体最基础的部分，回答"这个领域里有什么东西、它们之间是什么关系"。

| 元素 | 说明 | 示例 |
|------|------|------|
| 概念 | 领域中有意义的事物类型 | Order、Sku、User、Payment |
| 属性 | 概念的特征 | Order.totalAmountCents、Sku.priceCents |
| 关系 | 概念之间的关联 | Order 包含 OrderLineItem；Order 关联 User |
| 约束 | 跨概念的不变式 | 金额以分为单位；orderId 是全局关联键 |

### 动态（Dynamic）—— 会发生什么

定义领域中的核心流程、事件类型、因果链和状态机。这一层回答"这个领域里会发生什么事情、事情之间有什么因果关系"。

| 元素 | 说明 | 示例 |
|------|------|------|
| 流程 | 业务活动的骨架序列 | 下单 → 支付 → 履约 → 完成 |
| 事件 | 领域中有意义的状态变化 | OrderCreated、PaymentCompleted、StockReserved |
| 因果链 | 事件之间的导致关系 | OrderCreated → StockReserved → PaymentCompleted |
| 状态机 | 概念的生命周期 | Order: PENDING_PAYMENT → PAID → FULFILLING → COMPLETED |

动态维度不包含具体的业务策略（如"取消后 30 分钟退款"），只包含领域本质的流程结构。区分标准：去掉这个流程，业务还是不是同一个业务？

### 动能（Kinetic）—— 能做什么

定义对领域中的概念可以执行的有意义操作及其前置条件。这一层回答"对这些事物可以做什么"。

| 元素 | 说明 | 示例 |
|------|------|------|
| 操作 | 对概念有意义的动作 | Order 可以被创建、查询、取消 |
| 前置条件 | 操作的约束 | 取消：仅在 PENDING_PAYMENT 状态下 |
| 副作用 | 操作引发的连锁效果 | 创建订单 → 占用库存 + 创建支付单 |

动能维度描述"什么操作在业务上有意义"，但不描述"这些操作通过什么协议、什么接口暴露"。后者属于 MCP 工具设计。

---

## 本体不包含什么

| 内容 | 归属 | 原因 |
|------|------|------|
| MCP 工具的名称和参数设计 | MCP 工具 schema | 技术实现，不是领域真相 |
| API 端点和 HTTP 方法 | API 契约 (api.yaml) | 技术实现 |
| 具体的业务策略和可配置规则 | 各 BC 的 requirements.md | 可变的策略，不是不变的结构 |
| UI/UX 设计 | ui-spec.md | 展示层关注点 |
| 代码结构和实现细节 | 代码本身 | 解决方案域 |

## 本体与 MCP 的关系

本体和 MCP 是"描述"与"执行"的关系：

```
本体                              MCP
┌─────────────────────────┐      ┌─────────────────────────┐
│ 声明"对 Order 可以做      │      │ 实现"order_query 工具    │
│  创建、查询、取消"        │──→──│  接受 action 参数"       │
│                         │      │                         │
│ 声明"创建订单会           │      │ 实现"order_create 工具   │
│  占库存 + 创支付单"       │──→──│  内部编排多步操作"        │
└─────────────────────────┘      └─────────────────────────┘
   领域真相（不随技术变）            可执行投影（随技术演进）
```

MCP 工具的设计应该能从本体的动能声明中推导出来。当本体新增了一个概念或操作，MCP 工具应该跟着扩展。反之，如果一个 MCP 工具找不到本体中的对应声明，说明这个工具要么缺少本体支撑，要么不应该存在。

MCP Resource（领域知识）是本体在 AI 运行时的载体——它把本体中的规则和关系以 AI 可消费的形式注入到对话上下文中。

## 本体的三重作用

### 1. 给人看：共同语言

本体是业务、产品、开发之间的共同语言。当所有人对"订单""SKU""履约"的定义一致时，需求从传递到实现的失真大幅降低。

### 2. 给 AI 看：理解业务的锚点

本体通过 MCP Resource 注入 AI 的上下文，使 AI 从"调 API 的机器人"变成"理解业务的协作者"：

- AI 知道从 orderId 可以导航到 User、Payment、Fulfillment 的完整业务上下文
- AI 知道"库存占用"是下单时系统自动编排的，不该直接调用
- AI 知道 OrderCreated 之后应该发生 StockReserved，而不是 PaymentCompleted

### 3. 给信任链看：验证的基准

本体是代码实现和验收测试的基准线。领域模型代码应该和本体中的概念一一对应，验收测试验证的就是本体中声明的不变式和流程是否成立。

```
本体 ──定义──→ 领域模型 ──映射──→ 代码实现
  │                                    ↑
  └──定义──→ 业务规则 ──验证──→ 验收测试
```

## 同一份本体，两个消费者

本体最重要的特征之一是：**同一份文档在开发过程和产品运行时同时发挥作用。**

以 `hmall-ontology.md` 为例：

- **开发时**，它是 AI 开发助手（Cursor）的上下文。Cursor 读到"金额以分为单位"，就不会生成 `price = 5999.00` 这样的代码；读到"Order 包含 OrderLineItem"，就知道建模时该用组合而不是平铺。
- **运行时**，同一份文件通过 `hmall-mcp/resources/ontology.js` 被加载为 MCP Resource，注入到智能交互的系统提示词中。用户说"帮我查最近的订单"时，AI 知道金额要除以 100 再展示，知道从 orderId 能导航到支付和履约信息。

你不需要为"开发"维护一份模型，又为"产品"维护另一份。**同一份本体，同时被开发工具和产品功能消费**——这不是巧合，而是这套方法论的核心特征。

这意味着：对本体的每一次投资（补充一个概念、厘清一条关系、声明一个操作），都同时提升了开发效率和产品智能。反过来，如果本体缺失或不准确，两边同时受损。
