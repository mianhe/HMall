# BC 审计（只读）

对**指定限界上下文（BC）**做只读审计，产出分级整改清单与可执行建议。

---

## 审计目标

HMall 的开发体系依赖一条**信任链**：

```
领域模型 → 特性/场景 → 验收测试 → API 契约 → 代码实现
```

这条链保证了「测试通过 = 需求达成」。BC 审计的根本目标是：**验证这条链是否完整、各环节是否对齐。**

链条断裂的典型后果：

- 测试通过但实际行为不符合需求（特性 ↔ 测试脱节）
- 代码实现偏离领域模型，但无测试能捕获（模型 ↔ 实现脱节）
- 文档描述过时的行为，误导后续开发（文档 ↔ 现实脱节）
- 跨 BC 契约不一致，集成时才暴露问题

审计不是泛泛的"代码质量检查"，而是回答一个具体问题：**这个 BC 的验证体系是否值得信赖？**

---

## 何时使用 / 不使用

| 用 | 不用 |
|----|------|
| 评估 BC 的信任链完整性与测试可信度 | 已明确是单个 bug → `fix-bug-or-adjust-feature` |
| 盘点 BC 治理状态，形成整改计划 | 已明确要新增/演进特性 → `evolve-feature` |
| 重大变更前的健康摸底 | 立刻落地跨 BC 对接 → `integration` |

---

## 输入

- `target_bc`：要审计的 BC（如 `catalog`、`order`）
- `focus`（可选）：额外关注方向（如 `integration`、`test-trust`）

---

## 执行步骤

### 1) 建立审计基线

读取以下文档与代码，建立该 BC 的全貌认知：

**问题域文档**：

- `docs/bounded-contexts/<target_bc>/requirements.md`（特性与场景）
- `docs/bounded-contexts/<target_bc>/domain-model.md`
- `docs/bounded-contexts/<target_bc>/event-flow.md`（若存在）

**解决方案域资产**：

- `docs/bounded-contexts/<target_bc>/api.yaml`
- `features/<target_bc>/` 下的 .feature 文件
- `services/<target_bc>-service/` 下的代码与测试

**系统级文档**（按需参照）：

- `docs/context-map.md`
- `docs/business-flows.md`
- `docs/project-status.md`

### 2) 三维审计

按信任链从上游到下游的顺序检查。

#### 维度一：问题域完整性

验证 BC 的"业务定义"是否清晰、完整、自洽。

| 检查项 | 要点 |
|--------|------|
| 领域模型完整性 | 实体/值对象/聚合的属性、关系、不变式是否完整；是否有代码中存在但模型未描述的概念 |
| 特性覆盖度 | requirements.md 中的特性/场景是否覆盖了核心能力、异常路径、状态流转 |
| 事件流一致性 | event-flow 中的事件、命令、策略是否与 context-map 和实际实现一致 |
| 文档时效性 | 文档描述是否反映当前实现的真实行为 |

#### 维度二：链条对齐性（核心）

验证信任链各环节之间的对齐——这是审计的核心。

**环节对齐**：链条的每一环是否一一对应？

| 检查项 | 要点 |
|--------|------|
| 特性 → 验收测试 | 每个 Feature/Scenario 是否有对应的 .feature 场景？是否存在测试场景但 requirements.md 中无对应描述？ |
| 验收测试可信度 | 断言是否验证了场景的核心意图（而非只验证 HTTP 200）？异常路径（400/404/冲突）是否有验收覆盖？状态流转和不变式是否被测试守护？ |
| 领域模型 → 代码实现 | 代码中的实体、属性、行为是否忠实反映领域模型？是否有"模型里没有但代码里有"或"模型里有但代码里不一致"的偏差？ |
| API 契约 → 实现 | Controller 的路径、请求/响应结构是否与 api.yaml 一致？ |

**实现健康度**：代码实现能否持续忠实地承载领域模型？

代码质量问题不会直接让信任链断裂，但会让链条在演进中更容易断——冗余逻辑让修改容易遗漏分支，命名漂移让开发者误读意图，分层越界让职责纠缠。

| 检查项 | 要点 |
|--------|------|
| 分层边界 | 是否遵循 api → application → domain 的依赖方向？domain 层是否无外部依赖？ |
| 冗余与重复 | 是否有重复的业务逻辑（跨层或同层）？Step Definitions 是否有重复的 HTTP 调用模式？ |
| 死代码 | 是否存在已移除特性的残留代码、未使用的端口/适配器、废弃的 DTO？ |
| 命名一致性 | 代码中的类名、方法名、字段名是否与领域模型文档中的术语一致？是否存在同一概念多种称呼？ |

#### 维度三：集成边界

从该 BC 视角检查与外部 BC 的对接。

| 检查项 | 要点 |
|--------|------|
| 出站契约 | 出站端口（REST 调用、Kafka 发布）的语义、字段、错误码是否与下游 BC 的 API/事件定义一致 |
| 入站契约 | 入站适配器（Kafka Consumer、被调用 API）的字段与行为是否与上游 BC 的发布契约一致 |
| 测试隔离 | 跨 BC 调用在测试中是否通过 Stub/EventCapture 隔离？ |

### 3) 严重级分级

| 级别 | 含义 | 示例 |
|------|------|------|
| **P0** | **信任链断裂**：测试通过但行为可能不正确；或核心流程无测试守护 | 关键场景无验收覆盖；领域不变式未被测试守护；模型与代码行为不一致 |
| **P1** | **信任链薄弱**：验证存在但不充分，有漏网风险 | 异常路径缺失测试；文档描述过时；契约与实现有细微偏差 |
| **P2** | **治理改进**：不影响正确性但侵蚀链条耐久性 | 命名与领域术语漂移；跨层重复逻辑；已移除特性的残留代码；分层轻微越界 |

### 4) 输出审计结果

**每条发现包含**：

- `severity`（P0/P1/P2）
- `dimension`（问题域完整性 / 链条对齐 / 集成边界）
- `finding`：发现了什么
- `evidence`：文件路径、代码符号或测试名
- `impact`：对信任链的影响
- `action`：建议的修复方式及对应 Skill

**汇总部分**：

1. **信任链评估**：该 BC 信任链的整体健康度概述
2. **P0 问题清单**（若有）
3. **建议优先处理的 3 项**（跨级别，按修复价值排序）
4. **补测建议**（优先 Acceptance/Integration，必要时补 Unit）
5. **未验证项**（证据不足时如实声明）

## 关键约束

- **只读审计**：不直接改代码，只输出诊断
- **事实导向**：只基于仓库中可查证的事实，不臆测
- **证据必备**：每条发现必须给出可定位的证据
- **链条优先**：P0/P1 判定以对信任链的影响为核心标准，而非代码风格
- **测试策略**：以场景与契约为核心，优先 Acceptance/Integration，不以 Unit 数量为目标
- **衔接 Skill**：审计结束后由用户决定是否进入修复，切换到对应 Skill（`fix-bug-or-adjust-feature` / `evolve-feature` / `integration`）
