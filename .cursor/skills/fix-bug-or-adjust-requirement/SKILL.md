# 修复 Bug 或调整需求

针对**已有功能**的缺陷修复或需求微调，区别于「新增功能」的 ATDD 全流程。

| 阶段 | 目标 |
|------|------|
| 一、定位 | 弄清问题出在哪个环节（前端展示 / 后端 API / 上游数据） |
| 二、范围 | 确定需改动的模块与契约 |
| 三、实现 | 按依赖顺序修改（上游 → 下游 → 前端） |
| 四、验证 | 跑测试、必要时手动验证 |

---

## 步骤 To-Do

### 阶段一：定位

| 步骤 | 动作 |
|------|------|
| 1 | 理解用户描述的问题：缺什么、错什么、期望是什么 |
| 2 | 从**展示层**往回追溯：前端用到的字段、API 返回结构、数据来源（本 BC / 上游 BC） |
| 3 | 确定根因：数据缺失、字段错误、展示逻辑错误 |

### 阶段二：范围

| 步骤 | 动作 |
|------|------|
| 4 | 列出需改动的文件/模块：契约（api.yaml）、后端（领域/应用/基础设施/API）、前端、测试桩 |
| 5 | 若涉跨 BC：先改上游（提供方）再改下游（消费方） |

### 阶段三：实现

| 步骤 | 动作 |
|------|------|
| 6 | 按依赖顺序实现：契约 → 上游服务 → 下游适配器 → 下游 DTO/应用层 → 前端 |
| 7 | 保持向后兼容：新增字段用 optional/nullable；旧数据缺失时前端做兜底展示 |
| 8 | 更新测试桩（WireMock、Step Definitions）以匹配新契约 |

### 阶段四：验证

| 步骤 | 动作 |
|------|------|
| 9 | 运行相关服务测试：`mvn test -pl services/<service>` 或 `cd services/<service> && mvn test` |
| 10 | 若前端改动，可启动应用做手动验证 |

---

## 常见模式

| 问题类型 | 典型改动 |
|----------|----------|
| 展示信息不全 | 上游 API 增加字段 → 下游适配器解析并写入 DTO → 前端展示 |
| 展示格式不对 | 后端拼接/格式化（如「商品名 + SKU」）或前端格式化 |
| 缺少时间等元数据 | DTO 增加字段（如 `createdAt`）→ toDto 填充 → 前端格式化展示 |
| 历史数据无新字段 | 新字段 nullable；前端 `v-if="x"` 或兜底文案 |

## 检查清单

- [ ] 问题根因已定位
- [ ] 改动范围明确（契约、上游、下游、前端）
- [ ] 按依赖顺序实现
- [ ] 测试通过
- [ ] 契约文档（api.yaml）已同步
