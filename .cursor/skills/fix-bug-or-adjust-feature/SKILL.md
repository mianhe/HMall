# 修复 Bug 或调整特性

针对**已有特性**的缺陷修复或场景微调，区别于「新增/大改特性」的 ATDD 全流程。核心原则：**测试先行**——先让测试反映正确的期望行为（红），再改代码让测试通过（绿）。

| 阶段 | 目标 |
|------|------|
| 一、定位 | 弄清根因与改动范围 |
| 二、特性文档与测试先红 | 先更新特性文档，再调整测试用例，反映正确的期望行为 |
| 三、实现变绿 | 从域对象开始自内向外修改代码，让测试通过；**变绿后清理与重构** |
| 四、文档同步 | 更新领域模型、契约、事件流等文档 |
| 五、前端适配 | 若前端展示需调整，同步修改 |

---

## 步骤 To-Do

### 阶段一：定位

| 步骤 | 动作 |
|------|------|
| 1 | 理解用户描述的问题：现在的行为是什么、期望的行为是什么 |
| 2 | 从**展示层**往回追溯：前端 → API → 应用层 → 领域 → 上游 BC |
| 3 | 确定根因与改动范围：列出需改动的模块（测试、后端、契约、文档、前端） |

### 阶段二：特性文档与测试先红

| 步骤 | 动作 |
|------|------|
| 4 | **先更新特性文档**：检查 `requirements.md` 中的 Feature/Scenario 描述是否仍然准确。若修复揭示了遗漏的场景或不准确的描述，先在文档中修正/补充，再进入测试。这一步不可跳过——文档是测试的上游。 |
| 5 | 修改/新增验收测试（`.feature` 文件），使其**反映正确的期望行为**，与步骤 4 的文档一致 |
| 6 | 运行测试，确认测试**失败**（红）——证明测试能捕获当前的 bug |

> 若改动仅涉及前端展示，无后端行为变更，可跳过此阶段。

### 阶段三：实现变绿

| 步骤 | 动作 |
|------|------|
| 7 | **按 `design-principles.md` §2.4a 的实现顺序修改代码**：域对象 → 仓储 → 应用服务 → API/DTO，自内向外。每改完一层编译确认无类型不一致。 |
| 8 | 运行测试，确认测试**通过**（绿） |
| 8.5 | **清理与重构**（变绿后必做）：删除残留死代码、合并重复逻辑、确保命名与领域模型一致、整理 import 与代码风格。清理后再次运行测试确认仍全绿。详见下方「清理与整洁代码」。 |

### 阶段四：文档同步

| 步骤 | 动作 |
|------|------|
| 9 | 确认特性文档（`requirements.md`）在阶段二已更新。同步更新领域模型（`domain-model.md`）、事件流（`event-flow.md`）、API 契约（`api.yaml`）等 |
| 10 | 若涉及跨 BC 契约变更，同步更新上下文地图（`context-map.md`） |

### 阶段五：前端适配

| 步骤 | 动作 |
|------|------|
| 11 | 若前端展示/交互受影响，调整前端代码（文案、状态映射、交互逻辑） |
| 12 | 最终运行全部相关测试，确认无回归 |

---

### 清理与整洁代码（步骤 8.5）

| 要求 | 动作 |
|------|------|
| **代码简洁** | 删除中间/冗余代码；合并重复逻辑（如 Step Definitions 中重复 HTTP 调用）；移除无步骤的 Step Definition 类及其注册。 |
| **领域与代码一致** | 实体、聚合与 `domain-model.md` 一致；命名与不变式、领域行为与文档一致。有出入时先同步文档再改代码。 |
| **整洁代码** | 规范 import，避免全限定类名；统一 Optional/集合用法；Controller 只做 DTO 转换与调用应用服务；应用层不夹展示或基础设施细节；测试无重复断言逻辑。 |

> 清理完成后**必须**再跑一次测试确认仍全绿，再进入阶段四。

---

## 检查清单

- [ ] 问题根因已定位
- [ ] 特性文档（`requirements.md`）已检查并更新（遗漏场景已补充）
- [ ] 验收测试（`.feature`）已调整并验证先红后绿
- [ ] 代码遵循 `design-principles.md` §2.4a（从域对象自内向外、全链路类型一致）
- [ ] **清理与重构已完成**；验收仍全绿
- [ ] 文档已同步（领域模型、事件流、API 契约、上下文地图）
- [ ] 前端已适配（若涉及）
- [ ] 全部测试通过
