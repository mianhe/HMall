# 修复 Bug 或调整特性

针对**已有特性**的缺陷修复或场景微调（含前端 bug、集成/配置问题），区别于「新增/大改特性」的 ATDD 全流程。

核心原则：**复现先行，验证闭环**——先复现 bug，再定义验证标准，修完后自己验证通过，才能交付给用户。绝不把"请你验证一下"作为交付物。

| 阶段 | 目标 |
|------|------|
| 零、复现与验证计划 | 亲自复现 bug，定义"修好了"的验证标准 |
| 一、定位 | 弄清根因，判定改动范围与路径 |
| 二、特性文档与测试先红 | 先更新文档，再写/调测试，确认红 |
| 三、实现变绿 | 改代码/配置让测试通过；变绿后清理 |
| 四、自己验证 | 用阶段零定义的验证标准自己验证，失败则回到阶段一 |
| 五、文档同步与交付 | 文档同步，向用户报告验证结果 |

---

## 步骤 To-Do

### 阶段零：复现与验证计划（不可跳过）

| 步骤 | 动作 |
|------|------|
| 0a | **亲自复现**：不要凭代码推测，必须亲眼看到 bug。根据 bug 类型选择复现方式（见下表） |
| 0b | **记录复现证据**：截图、日志输出、HTTP 状态码等。这是后续对比"修好了"的基线 |
| 0c | **定义验证标准**：明确"修复成功"的判定条件（如"AI 助手问商品排名时，order_fact_query 工具被调用并返回数据，AI 正确展示商品名称和排名"） |
| 0d | **如果涉及多层链路**（如 前端→BFF→后端→MCP），在复现时追踪完整链路，识别断点在哪一层 |

**复现方式**：

| Bug 类型 | 复现方式 |
|----------|---------|
| 前端/UI bug | 用浏览器工具访问页面，实际操作触发 bug |
| API/后端 bug | `curl` 调用 API，查看返回 |
| AI 助手/MCP bug | 用浏览器访问管理后台 AI 助手实际提问，同时查看 smart-interaction 日志和 MCP 日志 |
| 部署环境 bug | SSH 到服务器，检查容器状态和日志 |
| 集成/配置 bug | 追踪完整调用链：检查每一层的配置和连通性 |

**多层链路追踪模板**（AI/MCP 类 bug 必做）：

```
□ Skill 配置：allowedTools 是否包含目标工具？
□ MCP 工具注册：目标工具是否在 MCP 的 tools/list 中？（检查入口文件 index.js / index-http.js）
□ MCP → 后端 API：工具调用的后端 API 是否可达？（curl 测试）
□ BFF 路由：API 路径是否被 BFF 正确转发？（生产环境经 Nginx→BFF→后端）
□ 后端数据：API 返回的数据是否非空/正确？
□ 服务重启：修改配置/MCP 后，相关服务是否已重启生效？
```

---

### 阶段一：定位

| 步骤 | 动作 |
|------|------|
| 1 | 基于复现结果，分析根因。从阶段零的链路追踪中已知断点在哪层 |
| 1a | **若问题发生在已部署环境**，先 SSH 诊断（参见 `server-diagnosis` 规则） |
| 2 | 确定根因与改动范围：列出所有需改动的点 |
| 3 | **判定路径**（见下表）。注意：一个 bug 可能涉及多个路径（如 MCP + BFF + Skill 配置），必须全部列出 |

**路径判定**：

| 路径 | 条件 | 验证手段 |
|------|------|---------|
| **后端路径** | 后端行为需变更（域/应用/API） | `.feature` 验收测试 |
| **前端路径** | 仅前端改动 | 浏览器验证 或 E2E 用例 |
| **集成/配置路径** | MCP 注册、Skill 数据、BFF 路由、Nginx 配置等 | 端到端链路验证（阶段零的链路追踪全部打勾） |
| **混合路径** | 多个路径组合 | 各路径验证手段组合 |

---

### 阶段二：特性文档与测试先红

#### 通用（所有路径必做）

| 步骤 | 动作 |
|------|------|
| 4 | **先更新特性文档**：检查 `requirements.md`（后端）或 `ui-spec.md`（前端）中的描述是否仍然准确。若修复揭示了遗漏的场景或不准确的描述，先在文档中修正/补充 |

#### 后端路径

| 步骤 | 动作 |
|------|------|
| 5-BE | 修改/新增验收测试（`.feature` 文件），使其反映正确的期望行为 |
| 6-BE | 运行验收测试，确认**失败**（红） |

#### 前端路径

| 步骤 | 动作 |
|------|------|
| 5-FE | 编写/修改 E2E 用例覆盖修复场景 |
| 6-FE | 运行 E2E 用例，确认**失败**（红） |

#### 集成/配置路径

| 步骤 | 动作 |
|------|------|
| 5-INT | 无需写测试文件，但必须在阶段零的链路追踪中明确标记当前哪些检查项是 ✗（失败） |
| 6-INT | 确认链路追踪中的 ✗ 项确实反映了 bug 的根因 |

---

### 阶段三：实现变绿

#### 后端路径

| 步骤 | 动作 |
|------|------|
| 7-BE | 按 `design-principles.md` §2.4a 实现顺序修改代码：域对象 → 仓储 → 应用服务 → API/DTO |
| 8-BE | 运行验收测试，确认**通过**（绿） |

#### 前端路径

| 步骤 | 动作 |
|------|------|
| 7-FE | 修改前端代码 |
| 8-FE | 运行 E2E 用例，确认**通过**（绿） |

#### 集成/配置路径

| 步骤 | 动作 |
|------|------|
| 7-INT | 修改配置/注册/路由等。**一次性修完所有已知断点**，不要改一个就交付 |
| 8-INT | 逐项确认链路追踪中之前为 ✗ 的检查项现在全部为 ✓ |

#### 通用（所有路径必做）

| 步骤 | 动作 |
|------|------|
| 8.5 | **清理与重构**（变绿后必做）：删除残留死代码、合并重复逻辑、确保命名一致、整理 import |
| 8.6 | **回归验证**（清理后必做）：后端路径运行全量验收测试；前端路径运行 Smoke P0 + 修复用例。确认仍全绿 |

---

### 阶段四：自己验证（不可跳过）

| 步骤 | 动作 |
|------|------|
| 9 | **用阶段零的相同方式复现**：用浏览器/curl/日志 重新执行阶段零的复现步骤 |
| 10 | **对比验证标准**：逐项检查阶段 0c 定义的验证条件是否全部满足 |
| 11 | **若验证失败**：记录失败现象，回到阶段一重新定位（可能遗漏了一层断点）。循环直到验证通过 |
| 12 | **若涉及部署环境**：提交推送 → 服务器拉取重部署 → 等待服务就绪 → 在服务器上再次验证 |

> **关键约束**：阶段四必须由自己完成，不能让用户代替验证。只有自己验证通过后，才能进入阶段五。

---

### 阶段五：文档同步与交付

| 步骤 | 动作 |
|------|------|
| 13 | 同步文档：后端同步 `domain-model.md`、`api.yaml` 等；前端同步 `ui-spec.md` |
| 14 | **向用户报告**，包括：问题根因、改动范围、验证结果（附截图/输出证据） |

---

### 清理与整洁代码（步骤 8.5）

| 要求 | 动作 |
|------|------|
| **代码简洁** | 删除中间/冗余代码；合并重复逻辑；移除无步骤的 Step Definition 类及其注册。 |
| **领域与代码一致** | 实体、聚合与 `domain-model.md` 一致；命名与不变式、领域行为与文档一致。 |
| **整洁代码** | 规范 import；Controller 只做 DTO 转换与调用应用服务；应用层不夹展示或基础设施细节。 |

> 清理完成后**必须**再跑回归验证（步骤 8.6）确认仍全绿，再进入阶段四。

---

## 检查清单

- [ ] **阶段零**：Bug 已亲自复现，验证标准已定义
- [ ] **阶段一**：根因已定位，路径已判定，所有断点已识别
- [ ] **阶段二**：特性文档已更新；测试先红已验证（或链路追踪 ✗ 项已标记）
- [ ] **阶段三**：实现变绿已验证；清理已完成；回归验证已通过
- [ ] **阶段四**：自己用阶段零的方式验证通过（附证据）
- [ ] **阶段五**：文档已同步；已向用户报告验证结果
