# 修复 Bug 或调整特性

针对**已有特性**的缺陷修复或场景微调（含前端 bug），区别于「新增/大改特性」的 ATDD 全流程。

核心原则：**测试先行，验证闭环**——先让测试反映正确的期望行为（红），再改代码让测试通过（绿），交付前开发者能自行验证。

| 阶段 | 目标 |
|------|------|
| 一、定位 | 弄清根因，判定改动范围与路径（后端 / 前端 / 混合） |
| 二、特性文档与测试先红 | 先更新文档，再写/调测试，确认红 |
| 三、实现变绿 | 改代码让测试通过；变绿后清理与重构 |
| 四、文档同步 | 更新领域模型、契约、事件流、ui-spec 等 |
| 五、开发者确认 | 提供验证方式，停顿让开发者确认 |

---

## 步骤 To-Do

### 阶段一：定位

| 步骤 | 动作 |
|------|------|
| 1 | 理解用户描述的问题：现在的行为是什么、期望的行为是什么 |
| 1a | **若问题发生在已部署环境**（如线上页面打不开、接口超时、服务异常），先 SSH 到服务器诊断：检查容器状态（`docker ps`）、查看服务日志（`docker logs`）、测试 API 连通性（`curl`）。确认是代码问题还是环境/运维问题后，再决定是否需要改代码。参见 `server-diagnosis` 规则 |
| 2 | 从**展示层**往回追溯：前端 → API → 应用层 → 领域 → 上游 BC |
| 3 | 确定根因与改动范围：列出需改动的模块（测试、后端、契约、文档、前端） |
| 3a | **判定路径**：根据改动范围选择对应路径，阶段二~三按路径分叉执行 |

**路径判定**：

| 路径 | 条件 | 阶段二的验证手段 |
|------|------|-----------------|
| **后端路径** | 后端行为需变更（域/应用/API） | `.feature` 验收测试 |
| **前端路径** | 仅前端改动，后端无变更 | **E2E 用例**（Playwright） |
| **混合路径** | 前后端均需改动 | `.feature` + E2E 用例 |

---

### 阶段二：特性文档与测试先红

#### 通用（所有路径必做）

| 步骤 | 动作 |
|------|------|
| 4 | **先更新特性文档**：检查 `requirements.md`（后端）或 `ui-spec.md`（前端）中的描述是否仍然准确。若修复揭示了遗漏的场景或不准确的描述，先在文档中修正/补充，再进入测试。**不可跳过。** |

#### 后端路径 / 混合路径

| 步骤 | 动作 |
|------|------|
| 5-BE | 修改/新增验收测试（`.feature` 文件），使其反映正确的期望行为 |
| 6-BE | 运行验收测试，确认**失败**（红） |

#### 前端路径 / 混合路径

| 步骤 | 动作 |
|------|------|
| 5-FE | 在 `tests/business-e2e/specs/` 或 `tests/smoke-e2e/specs/` 下编写/修改一个**最小 E2E 用例**，覆盖修复场景（如"结账页应出现镭雕输入区"） |
| 6-FE | 运行 E2E 用例，确认**失败**（红）——证明测试能捕获当前的 bug |

> **混合路径**同时执行 BE 和 FE 的步骤。

---

### 阶段三：实现变绿

#### 后端路径

| 步骤 | 动作 |
|------|------|
| 7-BE | **按 `design-principles.md` §2.4a 实现顺序修改代码**：域对象 → 仓储 → 应用服务 → API/DTO，自内向外。每改完一层编译确认无类型不一致 |
| 8-BE | 运行验收测试（`.feature`），确认**通过**（绿） |

#### 前端路径

| 步骤 | 动作 |
|------|------|
| 7-FE | 修改前端代码（页面、组件、API 调用等） |
| 8-FE | 运行步骤 5-FE 的 E2E 用例，确认**通过**（绿） |

#### 混合路径

先执行后端路径的 7-BE → 8-BE，再执行前端路径的 7-FE → 8-FE。

#### 通用（所有路径必做）

| 步骤 | 动作 |
|------|------|
| 8.5 | **清理与重构**（变绿后必做）：删除残留死代码、合并重复逻辑、确保命名一致、整理 import。详见下方「清理与整洁代码」 |
| 8.6 | **回归验证**（清理后必做）：后端路径运行全量验收测试；前端路径运行 **Smoke P0**（`npm run test:smoke:e2e:p0`）+ 修复用例。确认仍全绿 |

---

### 阶段四：文档同步

| 步骤 | 动作 |
|------|------|
| 9 | 确认特性文档在阶段二已更新。后端：同步 `domain-model.md`、`event-flow.md`、`api.yaml` 等。前端：同步 `ui-spec.md`（若交互/页面结构受影响） |
| 10 | 若涉及跨 BC 契约变更，同步更新 `context-map.md` |

---

### 阶段五：开发者确认

| 步骤 | 动作 |
|------|------|
| 11 | **提供验证信息**，包括：问题描述（现象 vs 期望）、改动范围（文件/逻辑）、验证命令（如 `npm run test:business:e2e -- --grep "BIZ-xxx"`）、受影响页面 URL |
| 12 | **停顿，请开发者确认。** 开发者可通过运行测试命令或访问页面来验证修复效果 |

---

### 清理与整洁代码（步骤 8.5）

| 要求 | 动作 |
|------|------|
| **代码简洁** | 删除中间/冗余代码；合并重复逻辑（如 Step Definitions 中重复 HTTP 调用）；移除无步骤的 Step Definition 类及其注册。 |
| **领域与代码一致** | 实体、聚合与 `domain-model.md` 一致；命名与不变式、领域行为与文档一致。有出入时先同步文档再改代码。 |
| **整洁代码** | 规范 import，避免全限定类名；统一 Optional/集合用法；Controller 只做 DTO 转换与调用应用服务；应用层不夹展示或基础设施细节；测试无重复断言逻辑。 |

> 清理完成后**必须**再跑回归验证（步骤 8.6）确认仍全绿，再进入阶段四。

---

## 检查清单

- [ ] 问题根因已定位，路径已判定（后端 / 前端 / 混合）
- [ ] 特性文档已检查并更新（`requirements.md` 和/或 `ui-spec.md`，遗漏场景已补充）
- [ ] **测试先红已验证**：后端 `.feature` 和/或前端 E2E 用例确认失败
- [ ] **实现变绿已验证**：后端验收和/或前端 E2E 用例确认通过
- [ ] 代码遵循 `design-principles.md`（后端从域对象自内向外；前端无业务逻辑硬编码）
- [ ] **清理与重构已完成**
- [ ] **回归验证已通过**：后端全量验收绿；前端 Smoke P0 绿 + 修复用例绿
- [ ] 文档已同步（领域模型、事件流、API 契约、上下文地图、ui-spec）
- [ ] **开发者确认**：已提供验证信息（问题描述、改动范围、验证命令、受影响页面），开发者已确认
