# 在 BC 内演进特性

在**已有**限界上下文中**新增、修改或移除**特性（.feature / Scenario）或接口。

| 阶段 | 目标 |
|------|------|
| 一、特性与模型 | 说清「改什么」与「改后领域长什么样」 |
| 二、契约与测试 | 定接口、写验收脚本，**先红** |
| 三、实现与验收 | 实现直到**全绿**，并完成清理与重构 |

遵循 `docs/design-principles.md`。文档路径：`docs/bounded-contexts/<上下文>/`；各服务内 feature 目录：`features/<上下文>/`。

---

## 跨 BC 需求

本 Skill 作用于**单个 BC**。若需求涉及**多个 BC**（如「超时未支付订单自动取消」横跨 Payment 与 Order），按以下方式处理：

1. **拆职责与验收点**：明确每个 BC 负责哪段行为、在哪个 .feature 里新增/修改哪些 Scenario。每个 BC 的 .feature 只断言本 BC 行为，不跨服务做端到端断言。
2. **定实现顺序**：通常**先下游（被调用方）后上游（调用方）**，使上游实现时下游契约与 internal API 已就绪。
3. **按 BC 分别演进**：对每个涉及的 BC 各执行一次本 Skill（阶段一 → 二 → 三）。
4. **集成验证（可选）**：跨服务联调或端到端验证另行安排，不塞进某个 BC 的 .feature。

---

## 关键确认点

**步骤 0、1、2、3、4** 为关键确认点，默认完成后停顿请确认。若用户要求「直接做完」「无需确认」等，可一气呵成。其余步骤自主连续执行。

---

## 步骤 To-Do

### 阶段一：特性与模型

| 步骤 | 动作 | 确认 |
|------|------|------|
| 0 | **确认目标 BC**：明确本次演进的 BC 是哪一个。若需求涉及多个 BC，先按上方「跨 BC 需求」拆分，确定本轮要演进的 BC 及顺序。 | 关键 |
| 1 | 读该 BC 的 `requirements.md`（承载的内容是特性）与用户指令。**已有特性**：引用相关条目，确认一致，有偏差则最小修改。**特性空缺**：在 requirements.md 中新增/修改/移除；移除特性时同步删除对应条目。 | 关键 |
| 2 | 在 .feature 中新增/修改/移除场景（Scenario），与特性一一对应。（步骤 2、3 顺序可调。） | 关键 |
| 3（若涉模型） | 在领域模型文档中更新实体、值对象、关系、不变式；修改/移除时明确列出变更 | 关键 |

### 阶段二：契约与测试（先红）

| 步骤 | 动作 | 确认 |
|------|------|------|
| 4（若涉及 API 变更） | 在 OpenAPI YAML 中更新 path/request/response，与模型及步骤 5 一致。不涉及新增/修改 API 时可跳过。 | 关键 |
| 5 | 更新 Step Definitions；跑验收，**预期相关场景红** | 自主 |

### 阶段三：实现与验收

| 步骤 | 动作 |
|------|------|
| 6 | 后端实现直到变绿：领域 → 基础设施 → 应用 → API。修改/移除时先改领域层再向外传播；移除死代码。若实现中需改模型，先更新文档并确认后再改代码。**出站端口/接口**：若新增了 Domain 层接口（如 `DomainEventPublisher`、`XxxPort`），除测试替身外，必须在 `infrastructure` 层提供**生产环境的默认实现**（NoOp/Logging + `@Component`，或 `@ConditionalOnMissingBean` 的 `@Bean`），确保无真实下游时也能启动。 |
| 7 | **清理与重构**（每完成一个 feature 必做）：按下方「清理与整洁代码」执行；验收保持全绿。 |
| 8（可选） | 前端对接：按后端返回展示。 |
| 9 | 更新 `docs/project-status.md`（若影响 scenario 数量、BC 职责或 MCP 覆盖）。 |

---

### 清理与整洁代码（步骤 7）

| 要求 | 动作 |
|------|------|
| **代码简洁** | 删除中间/冗余代码；合并重复逻辑（如 Step Definitions 中重复 HTTP 调用）；移除无步骤的 Step Definition 类及其注册。 |
| **领域与代码一致** | 实体、聚合、领域事件与 `domain-model.md` 一致；命名与不变式、领域行为与文档一致。有出入时先同步文档再改代码。 |
| **整洁代码** | 规范 import，避免全限定类名；统一 Optional/集合用法；Controller 只做 DTO 转换与调用应用服务；应用层不夹展示或基础设施细节；测试无重复断言逻辑。 |

---

## 异常：实现中需变更领域模型

更新领域模型文档 → 确认（默认停顿）→ 从内到外改代码，同步 feature/Step Definitions/前端 → 验收变绿。

## 检查清单

- [ ] 目标 BC 已确认；跨 BC 时已拆分并明确本轮 BC 与顺序
- [ ] 特性与特性文件（.feature）一致；涉模型则已更新
- [ ] 契约已更新（若涉及）；验收新增/修改场景先红
- [ ] 后端全绿；无死代码残留；项目状态已更新
- [ ] 新增的出站端口/Domain 接口均有**生产环境实现**（不仅仅是测试替身），`mvn spring-boot:run` 可启动
- [ ] 清理与重构已完成（简洁、领域一致、整洁代码）；验收仍全绿
