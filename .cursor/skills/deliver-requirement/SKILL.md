# 交付业务需求

从 `analyze-requirement` 产出的**迭代计划**出发，编排各 Skill 的执行顺序，跟踪完成进度，并在交付前通过端到端验收门禁确保业务链路可用。

**核心原则**：
1. 编排可以按复杂度简化，但 E2E 交付门禁不可跳过。
2. **E2E 必须自己跑通再交付**——设计用例 → 执行 → 失败则排查修复 → 再执行 → 全绿后才提交给开发者。中间不管遇到什么障碍（测试代码、前端代码、后端遗漏、BFF 路由、环境问题），都自行解决，不中断交给用户。

> Skill 体系总览与流程链见 `.cursor/skills/README.md`。

---

## 何时用 / 不用

| 用 | 不用 |
|----|------|
| `analyze-requirement` 完成后，需要执行迭代计划中的工作项 | 直接知道改哪个 BC 的哪个 Feature → `evolve-feature` |
| 需要跨多个 Skill 协调并最终验收一个业务需求 | Bug 修复或场景微调 → `fix-bug-or-adjust-feature` |
| 需要在交付前确保端到端链路可用 | 单纯的 BC 间对接（无业务需求上下文）→ `integration` |

**判断标准**：如果有 `overview.md` 迭代计划，并且该迭代包含 2 个以上工作项（多 BC / 含集成 / 含前端），就应该用本 Skill。

---

## Step 0：读取交付范围与模式选择

### 0a. 读取迭代计划

- 读 `docs/business-requirements/<name>/overview.md` 的迭代计划
- 确认当前要交付的是哪个迭代（若有多个迭代，按顺序逐个交付）
- 列出本迭代所有工作项：
  - 哪些 BC 需要 `evolve-feature`
  - 哪些 BC 间需要 `integration`
  - 哪些前端需要 `frontend-development`
  - E2E 验收条件（`BIZ-xxx` 标注）

### 0b. 确认依赖顺序

- 通常：先下游（被调用方）后上游（调用方）
- `integration` 在相关 BC 的 `evolve-feature` 都完成后执行
- `frontend-development` 在后端 API 就绪后执行
- E2E 门禁在所有工作项完成后执行

### 0c. 选择模式

| 模式 | 条件 | 行为差异 |
|------|------|---------|
| **轻量** | 单 BC + 单迭代 + 无跨 BC 集成 | 跳过编排跟踪表，直接列工作项清单 → 执行 → E2E 门禁 |
| **标准** | 多 BC 或多迭代或含跨 BC 集成 | 完整编排跟踪 + 依赖排序 + 逐项执行 + E2E 门禁 |

### 0d. 创建/更新交付跟踪（标准模式）

在 `overview.md` 末尾新增或更新「交付跟踪」章节：

```markdown
## 交付跟踪

### 迭代 N：<迭代名称>

| # | 工作项 | Skill | 依赖 | 状态 |
|---|--------|-------|------|------|
| 1 | <BC-A> 特性变更 | evolve-feature | — | ⬜ 待执行 |
| 2 | <BC-B> 特性变更 | evolve-feature | — | ⬜ 待执行 |
| 3 | <BC-A> → <BC-B> 集成 | integration | #1, #2 | ⬜ 待执行 |
| 4 | Web 前端对接 | frontend-development | #1, #2, #3 | ⬜ 待执行 |
| 5 | E2E 交付门禁 | deliver-requirement | #1–#4 | ⬜ 待执行 |
```

## Step 1：按序执行各工作项

按依赖顺序，逐一调度对应 Skill 执行各工作项：

- 每个工作项在**独立对话**中执行（避免上下文溢出）
- 完成一个工作项后，更新交付跟踪表状态（⬜ → 🔄 → ✅）
- 若执行中发现需要调整迭代计划（如新增集成、发现遗漏 BC），先更新计划再继续

**各 Skill 的调度要点**：

| Skill | 调度要点 |
|-------|---------|
| `evolve-feature` | 按迭代计划指定的 BC 和特性变更执行；若涉及多个 BC，先下游后上游 |
| `integration` | 在上下游 BC 的 evolve-feature 都完成后执行 |
| `frontend-development` | 后端 API 就绪后执行；Smoke P0 仍在 frontend-development 内部执行 |

> **注意**：本步骤是编排调度，具体的技术实现由各 Skill 自行负责。`deliver-requirement` 不介入 evolve-feature 内部的 ATDD 流程。

---

## Step 2：E2E 交付门禁（必做，不可跳过）

所有工作项完成后，执行端到端验收。这是交付前的**强制门禁**。

### 2a. Smoke P0 全量回归

在涉及的前端（admin / web）下执行：

```bash
cd frontend/<name> && npm run test:smoke:e2e:p0
```

确保既有核心链路未被破坏。若失败，排查是本次变更引入的回归还是环境问题。

> 若某个前端尚无 Smoke 基线（如 admin），跳过此步，仅执行 2b。

### 2b. Business E2E 验收

根据 `overview.md` 迭代计划中标注的 E2E 验收条件，在对应前端下编写并运行 Business E2E：

- 在 `tests/business-e2e/specs/<需求名>/` 下新增用例
- 用例命名格式：`BIZ-<需求缩写>-xxx 描述`
- 断言深度：验证业务链路能走通（操作链路端到端），不验证 UI 细节

**⚠️ 闭环要求（最重要的约束）**：

设计用例 → 执行 → **失败则排查修复** → 再执行 → **循环直到全绿**。

失败原因可能是：
- 测试代码本身的问题（选择器、等待、断言）
- 前端代码的问题（页面逻辑、交互 Bug）
- 后端或 BFF 的遗漏（路由未注册、API 不通）
- 环境问题（服务未重启到最新代码）

**无论哪种原因，都自行修复并重新执行，不中断交给用户。** 全绿后才进入下一步。

### 2c. 评估 Smoke 入选

从已通过的 Business E2E 中评估是否纳入 Smoke 长期守护：

| 级别 | 条件 |
|------|------|
| P0 | 核心交易链路（系统不可用级别） |
| P1 | 重要但非核心链路 |
| 不入选 | 非系统级可用性链路，仅保留 Business E2E |

### 2d. 准备验证环境 + 开发者确认

E2E 全绿后，**先准备好环境，再请开发者确认**：

1. **重启涉及代码变更的服务**（`./scripts/hmall.sh restart <services>`），确保用最新代码运行
2. **列出本迭代交付内容**：
   - 各 BC 的特性变更摘要
   - 前端变更（受影响页面 URL + 预期行为）
   - E2E 验收结果
3. **停顿，请开发者确认。** 开发者打开页面即可验证，无需自己排查环境。

---

## Step 2.5：迭代代码整理（E2E 全绿后、标记完成前）

E2E 全绿、开发者确认后，对本迭代变更的代码做一轮整理。**不改变行为**，有测试守护，整理后测试仍须全绿。

### 整理范围

扫一遍本迭代所有工作项涉及的变更文件（后端 + 前端 + 测试），按以下关注点逐项检查：

#### 后端（跨 BC 一致性）

| 关注点 | 动作 |
|--------|------|
| **命名统一** | 同一领域概念在不同 BC 中的命名是否一致（如 `engravingInfo` vs `serviceAttributes`，DTO 字段名 vs 域对象属性名） |
| **API 契约一致** | 请求/响应字段命名与 `api.yaml` 一致；BC 间调用的 DTO 字段命名互相对齐 |
| **重复代码** | 跨 BC 的 DTO 转换、工具方法是否有可合并或统一的模式 |

#### 前端

| 关注点 | 动作 |
|--------|------|
| **组件拆分** | 若 Vue 组件 `<script setup>` 超过 ~300 行或模板超过 ~200 行，考虑提取子组件或 composable |
| **逻辑提取** | 页面中重复或独立的业务逻辑（如镭雕内容处理、地址填充）可提取为 composable |
| **共享层整洁** | `shared/api/` 命名一致、无废弃函数；Page Object 方法命名清晰、无冗余方法 |
| **模板简化** | 过深的 `v-if` / `v-for` 嵌套可提取为具名组件或计算属性 |

#### 测试代码

| 关注点 | 动作 |
|--------|------|
| **E2E helper 整洁** | helper 函数命名清晰、无重复逻辑；Page Object 方法职责单一 |
| **选择器稳定性** | E2E 选择器优先使用 `getByRole`、`getByText`、`data-testid`，避免脆弱的 CSS 类选择器 |

### 执行方式

1. 列出本迭代变更的关键文件清单
2. 逐文件审查，按上述关注点做轻量整理（命名、提取、去重、简化）
3. **不做大规模重构**——如果发现需要较大的结构调整，记录为遗留项而非当场执行
4. 整理完后重新跑一遍验收测试（后端 `mvn test` + 前端 Smoke P0），确认无退化
5. 在交付跟踪中简要记录整理内容（如「整理：CheckoutPage 提取 composable、命名统一」）

---

## Step 3：迭代完成与后续

### 3a. 更新 overview.md 状态（逐项检查，不可遗漏）

完成以下**全部**更新，缺一不可：

| # | 位置 | 动作 | 示例 |
|---|------|------|------|
| 1 | 交付跟踪 → 工作项表 | 每行状态列改为 `✅ 完成` | `⬜ 待执行` → `✅ 完成` |
| 2 | 交付跟踪 → **迭代标题** | 加 `✅` | `### 迭代 1：xxx` → `### 迭代 1：xxx ✅` |
| 3 | 交付跟踪 → 迭代末尾 | 补**交付日期** + **下一迭代指引**（或"本需求已全部交付"） | `**交付日期**：2026-03-04` `**下一迭代**：迭代 2（yyy）` |
| 4 | 迭代计划（第四章）→ **迭代标题** | 加 `✅ 已完成` | `### 迭代 1：xxx` → `### 迭代 1：xxx ✅ 已完成` |

### 3b. 更新 `docs/project-status.md`（逐项检查）

| # | 位置 | 动作 |
|---|------|------|
| 1 | 功能演进路线表 | 更新该需求的状态列（如 `🔄 迭代 0、1 已完成，迭代 2 待开发`） |
| 2 | 各 BC 状态表 | 若 scenario 数量变化，更新说明列 |
| 3 | 变更日志 | 新增一行，记录本迭代交付内容 |

### 3c. 判断后续

| 情况 | 动作 |
|------|------|
| 还有后续迭代 | 标注下一个迭代，等待后续调用 |
| 这是最后一个迭代 | 执行 Step 4（需求级收尾） |
| 无迭代计划（轻量模式） | 直接执行 Step 4 |

---

## Step 4：需求级收尾（最后一个迭代完成后）

| 检查项 | 说明 |
|--------|------|
| 全量 Smoke 回归 | 各前端 `npm run test:smoke:e2e:p0` 确认 P0 链路全绿 |
| 所有迭代 E2E 回归 | 跑一遍所有迭代的 Business E2E，确认无退化 |
| 文档完整性 | `overview.md`：交付跟踪工作项 + 迭代标题 + 交付日期全部 ✅；迭代计划标题加 `✅ 已完成`；`project-status.md`：路线图 + BC 状态 + 变更日志已更新 |
| 遗留问题 | 若有已知限制或后续优化点，记录在 `overview.md` |

## 约定

| 约定 | 说明 |
|------|------|
| **E2E 全绿才交付** | 测试未通过不可停顿交给用户，自行排查修复直到全绿 |
| **环境随交付准备** | 提交开发者确认前，涉及变更的服务已重启、入口已告知 |
| **文档是状态载体** | 交付进度持久化在 `overview.md` 的交付跟踪章节，不依赖对话记忆 |
| **门禁不可跳过** | 无论轻量还是标准模式，E2E 交付门禁都是必做步骤 |
| **编排不介入实现** | `deliver-requirement` 只做调度和验收，不介入各 Skill 内部的技术决策 |
| **迭代独立可验收** | 每个迭代完成后都有独立的 E2E 验收，不积压到最后 |
| **迭代交付前必整理** | E2E 全绿后、标记迭代完成前，对本迭代变更代码做一轮轻量整理（Step 2.5），保持代码整洁 |
