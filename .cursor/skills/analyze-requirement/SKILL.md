# 分析业务需求

从一个**业务需求**出发，分析它对系统的影响，产出可执行的特性变更方案。

无论业务需求影响一个 BC 还是多个 BC，都走同一个流程。区别只是规模——影响面小时各步骤更轻量。

整体流程：**理解需求 → 事件流分析 → 领域建模 → 设计决策 → 产出方案（overview + 各 BC 特性变更）→ 一致性检查 → 系统文档更新**。各步骤可迭代。

> Skill 体系总览与流程链见 `.cursor/skills/README.md`。
> 事件驱动分析的理论说明见 `docs/architecture/event-driven-business-analysis.md`。

---

## 何时用 / 不用

| 用 | 不用 |
|----|------|
| 新建 BC | 已知某 BC 的某个特性要调整 → `evolve-feature` |
| 已有 BC 引入新的领域概念或跨 BC 交互 | Bug 修复或场景微调 → `fix-bug-or-adjust-feature` |
| 一个业务需求需要多个 BC 同时演进 | |

**判断标准**：如果开发者能直接说出"改哪个 BC 的哪个 Feature"，就不需要本 Skill。本 Skill 解决的是"还不清楚要改什么、改哪些 BC"的分析问题。

## Step 0：理解需求与前置读取

### 0a. 明确业务需求

| 维度 | 要回答的问题 |
|------|------------|
| **需求名称** | 简短业务名称 |
| **业务目标** | 用户/业务想达成什么？ |
| **后端影响面** | 可能涉及哪些 BC？哪些是核心变更、哪些仅需适配？ |
| **前端影响面** | 哪些前端页面需要新增或调整？（admin / web） |

### 0b. 选择分析深度

| 深度 | 适用场景 | 产出侧重 |
|------|----------|----------|
| **重流程** | 跨 BC 编排、异步与补偿多 | 事件流 + 领域建模 + Saga 设计 |
| **轻流程** | 流程较短或仅涉及少量 BC | 事件清单 + 领域建模 |
| **纯领域** | 无显著流程，以聚合建模为主 | 领域模型为主，事件仅作补充 |

### 0c. 前置读取

- `docs/context-map.md` 和 `docs/project-status.md`——了解系统全貌
- 所有可能受影响 BC 的已有文档（requirements.md、domain-model.md、event-flow.md）
- 关联 BC 的已有代码（Port 接口、事件消费者、状态枚举等）
- 可能受影响的前端界面规格（`docs/frontend/admin/ui-spec.md`、`docs/frontend/web/ui-spec.md`）——了解现有页面结构，判断哪些页面需要调整

## Step 1：事件流分析

**目标**：发现业务中发生的「事情」，建立时间线与因果关系。

- **重流程**：使用 Event Storming——领域事件、命令、策略、聚合，区分主流程与旁支
- **轻流程 / 纯领域**：列出事件清单即可
- 事件流以**业务需求整体**为视角，按业务场景画出事件链，标注每个事件/命令归属的 BC

**产出**：主流程事件链、逆向/补偿事件链、事件与命令/策略的对应关系。

---

## Step 2：领域建模

**目标**：识别聚合、实体、值对象，明确事件与领域对象的归属关系。

- 为每个事件追问：「这件事发生在哪个业务对象上？」
- 识别聚合根、子对象，将事件归类到对应聚合
- 按 BC 分组输出各 BC 的模型变更（新增/修改的聚合、实体、属性），标注 BC 间的新增关联
- 建模过程中会反哺事件流——发现缺失事件、合并或拆分事件

**产出**：领域模型图、事件清单（含所属聚合）、各聚合的状态/生命周期。

---

## Step 3：设计决策澄清

**目标**：逐一澄清关键设计决策。需要与用户讨论确认。

**典型决策维度**：

| 维度 | 要回答的问题 |
|------|------------|
| **同步 vs 异步** | 每个跨 BC 交互是同步调用还是事件驱动？ |
| **职责归属** | 某个业务逻辑由哪个 BC 负责？ |
| **状态推进规则** | 下游多实例状态不同步时，上游如何推进？ |
| **取消/补偿边界** | 什么状态下允许取消？补偿步骤是什么？ |
| **数据归属与快照** | 跨 BC 数据是快照还是引用？ |
| **建模方式** | 新概念如何融入已有模型？ |
| **MVP 范围** | 哪些能力先简化？ |

- 列出需要决策的问题，逐一与用户讨论
- 每个决策记录为 `{编号} | {决策} | {说明}`
- 决策可能反过来修改事件流和领域模型——这是正常的迭代

---

## Step 4：产出方案

分析成果落地为**两层文档**：

### 第一层：业务需求方案

写入 `docs/business-requirements/<name>/overview.md`：

| 章节 | 内容 |
|------|------|
| 背景与目标 | 为什么做、要达成什么 |
| 业务场景 | 核心场景描述 |
| 整体事件流 | 跨 BC 的事件链（如有） |
| 设计决策表 | Step 3 的决策记录 |
| 各 BC 影响摘要 | 每个 BC 的影响程度与核心变更概述 |
| 迭代计划（若需要） | 拆分为可独立验收的迭代，明确依赖顺序 |

**迭代计划中的前端变更**：每个迭代应包含**后端变更**和**前端变更**两部分。前端变更列出受影响的页面和变更要点（粗粒度：哪些页面、做什么），标注"后端完成后集成"。验收标准应覆盖到前端可操作。不需要在此写 UI Spec 细节——具体规格留到该迭代后端 API 契约确定后，由 `frontend-development` Skill 编写。

### 第二层：各 BC 特性变更

在各 BC 的 `requirements.md`、`domain-model.md`、`event-flow.md` 上增量修改：

- 标注变更点（🔄 需改 / 🔲 新增）
- 注明来源：`> 以下变更来自业务需求 [xxx](../../business-requirements/<name>/overview.md)`
- overview.md 回答「为什么」；各 BC 文档回答「做什么」——不重复解释业务背景
- 各 BC 的特性变更可直接作为 `evolve-feature` 的输入

---

## Step 5：一致性检查

| 检查维度 | 具体检查项 |
|----------|-----------|
| **BC 内一致** | 每个 scenario 都有领域模型支撑；API 契约字段与领域模型属性一致；事件 payload 与领域模型一致 |
| **跨 BC 一致** | 调用方 Port 签名与被调用方 API 契约一致；事件 payload 两侧一致；状态推进规则两侧一致 |
| **系统级一致** | context-map 集成关系与各 BC 文档一致；project-status 状态正确 |
| **业务需求一致** | overview.md 的设计决策与各 BC 文档的具体变更一致 |
| **前端覆盖完整** | 迭代计划的每个迭代都包含前端变更要点；后端新增/变更的 API 有对应的前端页面消费它；验收标准覆盖到前端可操作 |

---

## Step 6：系统文档更新

| 文档 | 更新内容 |
|------|---------|
| `docs/context-map.md` | BC 状态、集成关系表、事件总表 |
| `docs/project-status.md` | BC 状态表、路线图、决策记录、变更日志 |

## ⚠️ 分析完成后的衔接

分析产出方案后，**后续的每一个变更都必须通过对应的 Skill 流程执行**：

- 各 BC 的特性变更 → 逐一执行 `evolve-feature`（从阶段一"特性与模型"开始）
- Bug 修复或场景微调 → 执行 `fix-bug-or-adjust-feature`

**禁止在分析对话中直接修改代码、测试或域对象。** 分析阶段只产出文档（overview.md + 各 BC 文档增量变更），实现阶段必须切换到对应 Skill。

如果在分析讨论过程中产生了领域模型变更决策，应将决策记录在文档中，然后在执行 `evolve-feature` 时落地为代码——而不是"顺手改了"。

## 关键约定

| 约定 | 说明 |
|------|------|
| **事件优先** | 分析从事件入手，领域建模和 Saga 都以事件流为骨架 |
| **迭代精化** | 各步骤可多次往返，逐步收敛 |
| **决策先于实现** | 设计决策与用户确认后再编写特性，避免返工 |
| **两层文档** | overview.md 管「为什么」和「整体方案」；各 BC 文档管「做什么」和「怎么验收」 |
| **前端即时集成** | 每个迭代的规划包含前端变更要点，确保后端完成后前端可立即跟进。分析阶段只定要点（哪些页面、做什么），不写 UI Spec 细节——细节在后端 API 契约确定后由 `frontend-development` 编写 |
| **分析只产出文档，不产出代码** | 分析阶段的产出是文档变更，代码实现必须通过 `evolve-feature` 等 Skill 执行 |
