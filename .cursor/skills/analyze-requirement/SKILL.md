# 分析业务需求

从一个**业务需求**出发，分析它对系统的影响，产出可执行的特性变更方案。

无论业务需求影响一个 BC 还是多个 BC，都走同一个流程。区别只是规模——影响面小时各步骤更轻量。

整体流程：**理解需求 → 事件流分析 → 领域建模 → 设计决策 → 产出方案（overview + 各 BC 特性变更）→ 一致性检查 → 系统文档更新**。各步骤可迭代。

> Skill 体系总览与流程链见 `.cursor/skills/README.md`。
> 业务流程全景（事件流、路径枚举）见 `docs/business-flows.md`。

---

## 何时用 / 不用

| 用 | 不用 |
|----|------|
| 新建 BC | 已知某 BC 的某个特性要调整 → `evolve-feature` |
| 已有 BC 引入新的领域概念或跨 BC 交互 | Bug 修复或场景微调 → `fix-bug-or-adjust-feature` |
| 一个业务需求需要多个 BC 同时演进 | |

**判断标准**：如果开发者能直接说出"改哪个 BC 的哪个 Feature"，就不需要本 Skill。本 Skill 解决的是"还不清楚要改什么、改哪些 BC"的分析问题。

## Step 0：理解需求与前置读取

### 0a. 明确业务需求

| 维度 | 要回答的问题 |
|------|------------|
| **需求名称** | 简短业务名称 |
| **业务目标** | 用户/业务想达成什么？ |
| **需求类型** | 全新需求 or 已有需求的扩展场景？若是扩展，标注关联的已有需求，并决定是新建 overview 还是在已有 overview 中新增迭代 |
| **后端影响面** | 可能涉及哪些 BC？哪些是核心变更、哪些仅需适配？ |
| **前端影响面** | 哪些前端页面需要新增或调整？（admin / web） |

### 0b. 选择分析深度

| 深度 | 适用场景 | 产出侧重 |
|------|----------|----------|
| **重流程** | 跨 BC 编排、异步与补偿多 | 事件流 + 领域建模 + Saga 设计 |
| **轻流程** | 流程较短或仅涉及少量 BC | 事件清单 + 领域建模 |
| **纯领域** | 无显著流程，以聚合建模为主 | 领域模型为主，事件仅作补充 |

### 0c. 前置读取与影响面初判

- `docs/context-map.md` 和 `docs/project-status.md`——了解系统结构与 BC 集成关系
- `docs/business-flows.md`——了解现有业务流程（事件流、路径枚举），评估新需求对流程的影响
- 所有可能受影响 BC 的已有文档（requirements.md、domain-model.md、event-flow.md）
- 关联 BC 的已有代码（Port 接口、事件消费者、状态枚举等）
- 可能受影响的前端界面规格（`docs/frontend/admin/ui-spec.md`、`docs/frontend/web/ui-spec.md`）——了解现有页面结构，判断哪些页面需要调整

**影响面初判**：读完 `business-flows.md` 后，按其 §五「与需求分析的衔接」逐一回答 5 个检查问题（影响哪段、影响哪些事件、新增路径还是影响现有、是否打破 N2O ⊥ O2F、测试覆盖是否完整）。用此结果校正 0a 中的"后端影响面"，避免遗漏。

**复用初判**：对每个受影响 BC，标注其现有能力与本需求的关系（✅ 可直接复用 / 🔄 需调整 / 🔲 全新）。复用程度决定分析轻重——复用越多，分析越聚焦于增量部分。

## Step 1：事件流与查询影响分析

**目标**：发现业务中发生的「事情」，建立时间线与因果关系；同时识别受影响的查询场景。

- **以 `business-flows.md` 现有事件流为基线**，标注变化点（新增事件、修改触发条件、修改 payload），而非从白纸画起
- **重流程**：使用 Event Storming——领域事件、命令、策略、聚合，区分主流程与旁支
- **轻流程 / 纯领域**：列出事件清单即可
- 事件流以**业务需求整体**为视角，按业务场景画出事件链，标注每个事件/命令归属的 BC
- **查询影响**：除事件/命令（写路径）外，列出受影响的**查询场景**——例如：数据组装方式变化、唯一键语义变化导致的查询逻辑调整。查询影响容易被遗漏，但往往是 bug 的来源

**产出**：主流程事件链、逆向/补偿事件链、事件与命令/策略的对应关系、受影响的查询场景清单。

---

## Step 2：领域建模

**目标**：识别聚合、实体、值对象，明确事件与领域对象的归属关系。

- 为每个事件追问：「这件事发生在哪个业务对象上？」
- 识别聚合根、子对象，将事件归类到对应聚合
- 按 BC 分组输出各 BC 的模型变更（新增/修改的聚合、实体、属性），标注 BC 间的新增关联
- **不变式变更**：显式列出每个受影响聚合的不变式变化（唯一性约束、取值范围、状态转换规则等）。包括**业务前置条件**——某些场景要求特定业务状态已达成才能执行（如"商品已交付才能补购"），这些条件会成为新的不变式
- 建模过程中会反哺事件流——发现缺失事件、合并或拆分事件

**产出**：领域模型图、事件清单（含所属聚合）、各聚合的状态/生命周期、不变式变更清单。

---

## Step 3：设计决策澄清

**目标**：逐一澄清关键设计决策。需要与用户讨论确认。

**典型决策维度**：

| 维度 | 要回答的问题 |
|------|------------|
| **同步 vs 异步** | 每个跨 BC 交互是同步调用还是事件驱动？ |
| **职责归属** | 某个业务逻辑由哪个 BC 负责？ |
| **查询编排** | 跨 BC 数据组合由谁负责？前端编排 / BFF 聚合 / BC 聚合 API？ |
| **状态推进规则** | 下游多实例状态不同步时，上游如何推进？ |
| **取消/补偿边界** | 什么状态下允许取消？补偿步骤是什么？ |
| **数据归属与快照** | 跨 BC 数据是快照还是引用？ |
| **建模方式** | 新概念如何融入已有模型？ |
| **MVP 范围** | 哪些能力先简化？ |

- 列出需要决策的问题，逐一与用户讨论
- 每个决策记录为 `{编号} | {决策} | {说明}`
- 决策可能反过来修改事件流和领域模型——这是正常的迭代

---

## Step 4：产出方案

分析成果落地为**两层文档**：

### 第一层：业务需求方案

写入 `docs/business-requirements/<name>/overview.md`：

| 章节 | 内容 |
|------|------|
| 背景与目标 | 为什么做、要达成什么 |
| 业务场景 | 核心场景描述 |
| 整体事件流 | 跨 BC 的事件链（如有） |
| 复用分析（扩展型需求） | 已有能力与本需求的关系（✅ 可复用 / 🔄 需调整 / 🔲 全新），明确前置依赖 |
| 设计决策表 | Step 3 的决策记录 |
| 各 BC 影响摘要 | 每个 BC 的影响程度与核心变更概述 |
| 迭代计划（若需要） | 拆分为可独立验收的迭代，明确依赖顺序 |

**迭代计划中的前端变更**：每个迭代应标注受影响的前端页面和变更要点（粗粒度：哪些页面、做什么）。不需要写 UI Spec 细节——具体规格留到后端 API 契约确定后，由 `frontend-development` Skill 编写。

**迭代计划中的 E2E 验收**：引入新业务路径的迭代必须标注 **E2E 验收条件**——用例 ID 前缀（如 `BIZ-SP-001`）和验收场景概述。此标注是 `deliver-requirement` 执行 E2E 交付门禁的依据。未标注的迭代视为不需要新增 E2E。

### 第二层：各 BC 特性变更

在各 BC 的 `requirements.md`、`domain-model.md`、`event-flow.md` 上增量修改：

- 标注变更点（🔄 需改 / 🔲 新增）
- 注明来源：`> 以下变更来自业务需求 [xxx](../../business-requirements/<name>/overview.md)`
- overview.md 回答「为什么」；各 BC 文档回答「做什么」——不重复解释业务背景
- 各 BC 的特性变更可直接作为 `evolve-feature` 的输入

---

## Step 5：一致性检查

分析阶段的一致性检查范围限于**问题域文档**（overview、requirements、domain-model、event-flow）。API 契约（`api.yaml`）属于解决方案域，由 `evolve-feature` 在阶段二更新，不在此检查。

| 检查维度 | 具体检查项 |
|----------|-----------|
| **BC 内一致** | 每个 scenario 都有领域模型支撑；事件 payload 与领域模型一致；不变式变更后，相关查询逻辑（数据组装、去重、聚合方式）与新模型一致；模型图与属性表一致（多重性、可选性） |
| **跨 BC 一致** | 事件 payload 两侧 BC 文档一致；状态推进规则两侧一致 |
| **系统级一致** | context-map 集成关系与各 BC 文档一致；project-status 状态正确 |
| **业务需求一致** | overview.md 的设计决策与各 BC 文档的具体变更一致 |
| **流程影响完整** | 对照 `business-flows.md`：新增路径已补充（§四）？事件流是否需要更新（§二）？事件总表是否需要更新（§三）？E2E 测试覆盖是否需要更新？ |
| **前端影响已标注** | 迭代计划的每个迭代都标注了受影响的前端页面和变更要点 |

| 文档 | 更新内容 |
|------|---------|
| `docs/context-map.md` | 上下文说明表（BC 状态）、集成关系表 |

## ⚠️ 分析完成后的衔接

分析产出方案后，**交由 `deliver-requirement` 编排后续交付**：

1. **有迭代计划时** → 调用 `deliver-requirement`，由它按迭代计划编排各 Skill 的执行顺序、跟踪进度、并执行 E2E 交付门禁
2. **无需编排时**（如仅涉及单个 BC 的单个特性调整） → 可直接执行 `evolve-feature`，但交付前仍建议通过 `deliver-requirement` 执行 E2E 门禁

**禁止在分析对话中直接修改代码、测试或域对象。** 分析阶段只产出文档（overview.md + 各 BC 文档增量变更），实现阶段必须切换到对应 Skill。

如果在分析讨论过程中产生了领域模型变更决策，应将决策记录在文档中，然后在执行 `evolve-feature` 时落地为代码——而不是"顺手改了"。

## 关键约定

| 约定 | 说明 |
|------|------|
| **事件优先** | 分析从事件入手，领域建模和 Saga 都以事件流为骨架 |
| **迭代精化** | 各步骤可多次往返，逐步收敛 |
| **决策先于实现** | 设计决策与用户确认后再编写特性，避免返工 |
| **两层文档** | overview.md 管「为什么」和「整体方案」；各 BC 文档管「做什么」和「怎么验收」 |
| **前端影响前置识别** | 分析阶段即标注每个迭代的前端影响面（哪些页面、做什么），为 `deliver-requirement` 编排前端工作提供输入 |
| **分析只产出文档，不产出代码** | 分析阶段的产出是文档变更，代码实现必须通过 `evolve-feature` 等 Skill 执行 |
