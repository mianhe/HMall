# 分析业务需求

从一个**业务需求**出发，分析它对系统的影响，产出可执行的特性变更方案。整体分为两个阶段：

- **Phase A（分析）**：理解需求 → 流程盘点 → 事件分析 → 领域建模 → 产出 overview.md。**仅写 overview.md，不触碰 BC 文档和系统文档。**
- **Phase B（落地）**：用户明确指令后，将 overview 中的变更规格分发到各 BC 文档 + 更新系统文档。

Phase A 完成后不自动进入 Phase B——overview.md 可以长期作为独立的需求方案存在。

**核心原则：主价值流重事件，支撑流程轻流程，异常流程补关键事件链。**

> Skill 体系总览见 `.cursor/skills/README.md`，业务流程全景见 `docs/business-flows.md`。

---

## 何时用 / 不用

| 用 | 不用 |
|----|------|
| 新建 BC | 已知某 BC 的某个特性要调整 → `evolve-feature` |
| 已有 BC 引入新的领域概念或跨 BC 交互 | Bug 修复或场景微调 → `fix-bug-or-adjust-feature` |
| 一个业务需求需要多个 BC 同时演进 | |

**判断标准**：如果开发者能直接说出"改哪个 BC 的哪个 Feature"，就不需要本 Skill。本 Skill 解决的是"还不清楚要改什么、改哪些 BC"的分析问题。

## 用户交互

### 入口卡场景、过程靠判断、出口看整体

| 时机 | 做什么 | 约束 |
|------|--------|------|
| **入口确认**（Step 1 后） | 展示流程清单，问「场景有没有遗漏」 | **硬停点**——未获用户回复前不进入 Step 2 |
| **过程按需互动**（Step 2-3） | 碰到重大且不确定的问题，及时提出 | 没有大问题就继续推进，不要为了问而问 |
| **出口确认**（overview 完成后） | 请用户审阅，问「有没有问题或需要调整的地方」 | 用户确认后 Phase A 结束 |

### 什么值得在过程中停下来问

**要问**（影响大 + 不确定）：
- 判断错了会导致模型结构性返工（如某概念归哪个 BC、同步 vs 异步）
- 两种方案都合理，但走向完全不同
- 用户需求描述有歧义，两种理解差异大

**不用问**：
- 技术实现细节——这是 Agent 的职责，做错了用户会纠正
- 有明显更优方案的选择
- 后续容易调整、不会大返工的细节

### 提问方式

不强制使用特定工具。可以用 AskQuestion 工具提供选项，也可以直接在回复中结构化提问（编号 + 选项 + 简短说明）。形式不重要，**让用户看得清楚、回复方便**就行。

## Step 0：理解需求与前置读取

### 0a. 明确业务需求

| 维度 | 要回答的问题 |
|------|------------|
| **需求名称** | 简短业务名称 |
| **业务目标** | 用户/业务想达成什么？ |
| **需求类型** | 全新需求 or 已有需求的扩展？若扩展，标注关联需求，决定新建 overview 还是在已有 overview 中新增迭代 |
| **后端影响面** | 可能涉及哪些 BC？哪些核心变更、哪些仅需适配？ |
| **前端影响面** | 哪些前端页面需新增或调整？（admin / web） |

### 0b. 前置读取与影响面初判

- `docs/context-map.md` 和 `docs/project-status.md`——系统结构与 BC 集成关系
- `docs/business-flows.md`——现有业务流程，评估新需求对流程的影响
- 所有可能受影响 BC 的文档（requirements.md、domain-model.md、event-flow.md）
- 关联 BC 的已有代码（Port 接口、事件消费者、状态枚举等）
- 前端界面规格（`docs/frontend/admin/ui-spec.md`、`docs/frontend/web/ui-spec.md`）

**影响面初判**：读完 `business-flows.md` 后，按其 §五「与需求分析的衔接」逐一回答 5 个检查问题，校正 0a 的影响面判断。

**复用初判**：对每个受影响 BC，标注现有能力与本需求的关系（✅ 可直接复用 / 🔄 需调整 / 🔲 全新）。

## Step 1：流程盘点（→ 入口确认）

**目标**：把需求涉及的所有业务流程列出来、分好层，避免遗漏隐性流程。

### 1a. 识别并列出流程

将需求拆为三类：

| 类型 | 含义 | 例子 |
|------|------|------|
| **主流程** | 直接产生用户价值的端到端流程 | 下单→支付→履约→签收 |
| **支撑流程** | 为主流程提供能力或配置 | Admin 配置可选项、维护规则 |
| **异常流程** | 取消、失败、补偿、降级 | 支付超时取消、生产失败重试 |

每条流程一句话描述：`谁 → 做什么 → 产生什么业务结果`。

### 1b. 为每条流程选择分析深度

| 深度 | 代号 | 适用场景 | 产出 |
|------|------|----------|------|
| **重** | L3 | 跨 BC、状态推进复杂、有补偿 | 事件链 + 命令 + 策略 + 状态门禁 |
| **中** | L2 | 有少量状态变化但不复杂 | 事件清单 + 影响 BC + 验证点 |
| **轻** | L1 | CRUD / 配置型、无显著状态流转 | 操作描述 + 对主流程的影响规则 |

选择原则：主流程 → L3（必须），支撑流程 → L1/L2（按复杂度），异常流程 → 至少列出关键事件链。

**产出**：流程清单表（流程名 + 类型 + 分析深度 + 一句话描述）。

### ✅ 入口确认（硬停点）

展示流程清单表，问用户「场景有没有遗漏？」。如有需要用户选择的建模方向，附带一起问。**未获用户回复前，不进入 Step 2。**

---

## Step 2：分级事件分析

**目标**：按 Step 1 确定的深度，逐条流程做事件分析。先看"发生了什么事"（Event），再追"谁触发了什么操作"（Command），最后补"系统自动规则"（Policy）。

**以 `business-flows.md` 现有事件流为基线**，标注变化点（新增事件、修改触发条件、修改 payload），而非从白纸画起。

### 2a. L3 重分析：完整事件驱动

按时间线展开，使用标准事件流表（`# | Event 🟧 | Command ⌘ | Policy/Rule ⟳ | BC | 影响识别`）。

> 各列含义与格式详见 [`assets/overview-template.md`](./assets/overview-template.md)。

BC 列仅标事件归属方（发布者），消费方的反应写在 Policy 列。主成功路径和补偿路径分别建表。

必须覆盖：主成功路径 + 补偿/逆向路径 + 状态门禁。

### 2b. L2 中分析：关键事件清单

列出关键事件和状态变化：事件名 + 触发条件 + 影响的 BC + 对主流程的影响点。

### 2c. L1 轻分析：流程步骤与影响边界

自然语言描述操作步骤，重点说清**对主流程的影响边界**（如"配置变更仅影响新订单，不影响历史快照"）。

### 2d. 查询影响分析

列出受影响的查询场景——数据组装方式变化、唯一键语义变化等。查询影响容易遗漏，往往是 bug 来源。

### 2e. 流程间耦合分析

- 支撑流程的产出如何被主流程消费（实时引用 vs 快照）
- 支撑流程变更是否影响主流程的已有实例
- 异常流程是否需要跨流程补偿

### 2f. 数据可达性检查（仅 L3）

事件流表抓住了**控制流**（谁触发谁），但不验证**数据流**（做决策需要的信息模型里有没有）。对 L3 事件流中涉及**决策、分支、类型判断、门禁**的 Command 和 Policy，逐一验证：

1. **做这个决策需要什么信息？**——从 Policy/Command 出发
2. **信息在哪个模型字段上？**——追溯到具体 BC.聚合.字段
3. **跨 BC 时传递链完整吗？**——源 BC 字段 → API/事件 payload → 目标 BC 字段
4. **现有模型是否具备？**——✅ 已有 / ❌ 缺失

所有 ❌ 项必须在 Step 3 建模时补齐——它们往往意味着需要新增领域概念或拆分已有枚举。

**产出**：每条流程的事件分析 + 流程间耦合关系 + 查询影响清单 + L3 数据可达性验证。

> 分析中碰到重大不确定的决策点，按 §用户交互 判断是否需要及时向用户提出。

---

## Step 3：领域建模

**目标**：识别聚合、实体、值对象，明确事件与领域对象的归属关系。

- 为每个事件追问：「这件事发生在哪个业务对象上？」
- 识别聚合根、子对象，将事件归类到对应聚合
- 按 BC 分组输出模型变更（新增/修改的聚合、实体、属性），标注 BC 间新增关联
- **补齐 2f 数据缺口**：所有 ❌ 项在此步骤落实为具体的模型字段或概念新增
- **不变式变更**：显式列出每个受影响聚合的不变式变化（唯一性约束、取值范围、状态转换规则等），包括业务前置条件
- 建模过程中会反哺事件流——发现缺失事件、合并或拆分事件

**产出**：领域模型图、事件清单（含所属聚合）、各聚合的状态/生命周期、不变式变更清单。

---

## Step 4：产出 overview.md（→ 出口确认）

### 4a. 收敛设计决策

写 overview 前，回顾 Step 2-3 积累的决策，对照以下维度检查遗漏：

**通用维度**：同步 vs 异步、职责归属、查询编排、状态推进规则、取消/补偿边界、数据归属与快照、建模方式、MVP 范围。

**常见必答项**（已在分析中覆盖的标"已确认"，有遗漏的补充）：

| 决策项 | 说明 |
|--------|------|
| 冻结点 | 用户提交的内容在何时成为不可变快照？ |
| 配置变更影响范围 | 后台配置变更是否影响已有实例？ |
| 取消与补偿边界 | 各状态下取消是否允许？补偿步骤？ |
| 数量语义 | 批量场景下，定制内容按整批统一还是逐件独立？ |
| 内容治理等级 | 用户输入的校验级别？ |
| 生效范围 | 新能力按全局还是按特定对象绑定？ |

如果仍有重大未决项，向用户提出后再继续。

### 4b. 编写 overview

产出 `docs/business-requirements/<name>/overview.md`。**不修改任何 BC 文档和系统文档。**

> **编写前必须先读取 [`assets/overview-template.md`](./assets/overview-template.md)**——其中定义了章节结构（§一～§五）、事件流表格式、§四 变更规格的子节定义与示例。

各 Step 产出 → overview 章节映射：

| 分析步骤产出 | overview 章节 |
|-------------|-------------|
| Step 0 需求理解 | §一 背景与目标 |
| Step 1 流程清单 | §二 场景总览表 |
| Step 2 事件分析 + 数据可达性 | §二 各场景展开（事件流表、数据依赖验证、查询影响等） |
| Step 3 领域建模 | §四 各 BC 领域模型变更 |
| Step 2+3 综合 | §四 各 BC 事件流变更、需求场景变更 |
| 设计决策 | §三 设计决策表 |

**关键约束**：
- **§四 是 Phase B 的唯一输入源**——必须详细到可直接落地，不是摘要
- §二（跨 BC 横切）与 §四（单 BC 纵切）互补、不重复

### 4c. 一致性检查

| 检查维度 | 检查项 |
|----------|--------|
| 流程完整 | 所有流程已盘点？主流程都做了 L3？支撑流程说明了影响边界？ |
| 事件完整 | L3 流程覆盖主成功路径 + 补偿路径？状态门禁无遗漏？ |
| 数据可达 | L3 数据依赖表中所有 ❌ 项在 §四 模型变更中已补齐？跨 BC 传递链在 BC 间数据流中有对应？ |
| §二 ↔ §四 一致 | §二 的每个 BC 影响在 §四 有对应变更规格，反之亦然 |
| §四 内部一致 | 需求场景有模型支撑；payload 与模型属性一致；不变式与状态机一致 |
| §四 跨 BC 一致 | 事件 payload 发布方和消费方一致；数据流源/目标对应正确 |
| §三 ↔ §四 一致 | 设计决策与变更规格不矛盾 |
| 前端影响 | 迭代计划标注了受影响页面和变更要点 |

### ✅ 出口确认

overview 完成后，请用户审阅，问「整体方案有没有问题或需要调整的地方」。用户确认后 Phase A 结束。

---

> **Phase A 到此结束。** overview.md 是自包含的需求方案，可长期独立存在。以下 Phase B 仅在用户明确指令时执行。

## Phase B：落地到各 BC

**触发条件**：用户明确说"落地到 BC"、"更新 BC 文档"、"准备开发"或类似指令。不可自动执行。

### 更新各 BC 问题域文档

以 overview §四 为输入：

| BC 文档 | 操作 |
|---------|------|
| `requirements.md` | 新增/修改验收场景，标注 🔲/🔄 |
| `domain-model.md` | 新增/修改聚合、实体、值对象、不变式、状态机；更新 PlantUML 图 |
| `event-flow.md` | 新增/修改 API 契约、事件契约、集成关系 |

每处注明来源：`> 以下变更来自业务需求 [xxx](../../business-requirements/<name>/overview.md)`

### 更新系统文档

| 文档 | 更新内容 |
|------|---------|
| `docs/context-map.md` | BC 状态、集成关系 |
| `docs/business-flows.md` | 事件流、事件总表、路径枚举 |
| `docs/project-status.md` | BC 状态、路线图、决策记录、变更日志 |

### 跨文档一致性检查

| 检查维度 | 检查项 |
|----------|--------|
| BC 内一致 | 场景有模型支撑；payload 与模型一致；图与表一致 |
| 跨 BC 一致 | 事件 payload 两侧一致；状态推进规则两侧一致 |
| 系统级一致 | context-map 与 BC 文档一致；business-flows 与各 event-flow 一致 |
| overview ↔ BC 一致 | §四 每条变更规格已落地，无遗漏无矛盾 |

## 衔接

**Phase A 后**：用户可审阅讨论、搁置调整、执行 Phase B、或直接调用 `deliver-requirement`。

**Phase B 后**：调用 `deliver-requirement` 按迭代计划编排执行，或单 BC 场景直接 `evolve-feature`。

## 关键约定

| 约定 | 说明 |
|------|------|
| Phase A 只写 overview | 不触碰 BC 文档和系统文档 |
| Phase B 需明确触发 | 用户明确说"落地"时才执行，不可自动进入 |
| overview 自包含 | §四 的变更规格必须详细到可直接落地，不是摘要 |
| 分级分析 | 主价值流重事件，支撑流程轻流程，异常流程补关键事件链 |
| 事件驱动 | L3 分析骨架：Event → Command → Policy → Impact |
| 只产出文档 | 分析阶段不修改代码、测试或域对象 |
