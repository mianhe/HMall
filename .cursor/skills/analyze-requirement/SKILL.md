# 分析业务需求

从一个**业务需求**出发，分析它对系统的影响，产出可执行的变更方案。

**核心理念：设计过程即文档编写过程。** 每一步直接写入 overview.md 的对应章节，写完即与用户基于文档内容确认——不存在"先在脑子里分析，最后再写文档"的割裂。

**分级原则：主价值流重事件，支撑流程轻流程，异常流程补关键事件链。**

---

## 两个阶段

- **Phase A（分析）**：逐章节写入 `docs/business-requirements/<name>/overview.md`。**仅写 overview.md，不触碰 BC 文档和系统文档。**
- **Phase B（落地）**：用户明确指令后，将「变更分析」分发到各 BC 文档 + 更新系统文档。

Phase A 完成后不自动进入 Phase B——overview.md 可长期作为独立的需求方案存在。

> Skill 体系总览见 `.cursor/skills/README.md`，业务流程全景见 `docs/business-flows.md`。

---

## 何时用 / 不用

| 用 | 不用 |
|----|------|
| 新建 BC | 已知某 BC 的某个特性要调整 → `evolve-feature` |
| 已有 BC 引入新的领域概念或跨 BC 交互 | Bug 修复或场景微调 → `fix-bug-or-adjust-feature` |
| 一个业务需求需要多个 BC 同时演进 | |

**判断标准**：如果开发者能直接说出"改哪个 BC 的哪个 Feature"，就不需要本 Skill。本 Skill 解决的是"还不清楚要改什么、改哪些 BC"的分析问题。

---

## 用户交互原则

**每章写完即是一次轻量确认。** 文档本身就是沟通媒介——写完一章，用户自然能看到内容并给出反馈。最终的整体确认是水到渠成的事。

**每章写完后**：简要告知用户本章写了什么、有什么关键判断。如有需要用户抉择的问题（建模方向、两种方案差异大等），附带提出。用户没有异议就推进下一章。

**什么值得停下来问**（适用于任何章节）：
- 判断错了会导致模型结构性返工（如概念归属、同步 vs 异步）
- 两种方案都合理但走向完全不同
- 需求描述有歧义，两种理解差异大

**什么不用问**：
- 技术实现细节——做错了用户会纠正
- 有明显更优方案的选择
- 后续容易调整的细节

## Phase A：逐章节分析

overview.md 由四章 + 交付跟踪组成：**需求概述与场景 → 场景分析（事件流） → 变更分析 → 迭代计划 → 交付跟踪**。前四章对应分析步骤，交付跟踪由 `deliver-requirement` 在执行交付时写入。每章写完即交付确认。

### 准备：前置读取

开始分析前，读取以下文档建立上下文：

- `docs/context-map.md`、`docs/project-status.md`——系统结构与 BC 集成关系
- `docs/business-flows.md`——现有业务流程；按其第七章「需求分析检查清单」逐一回答检查问题，初判影响面
- 若为扩展型需求，读取关联的已有业务需求 overview（如镭雕依赖虚拟商品，应先读 `virtual-product/overview.md`）
- 所有可能受影响 BC 的文档（requirements.md、domain-model.md、event-flow.md）
- 关联 BC 的已有代码（Port 接口、事件消费者、状态枚举等）
- 前端界面规格（`docs/frontend/admin/ui-spec.md`、`docs/frontend/web/ui-spec.md`）
- [`assets/overview-template.md`](./assets/overview-template.md)——overview 文档格式与约定

读完后创建 `docs/business-requirements/<name>/overview.md`，开始逐章写入。

### Step 1：写第一章「需求概述与场景」

**做什么**：理解需求、盘点场景。这是用户看到的第一个交付，应同时回答"需求是什么"和"涉及哪些场景"。

**上半部分——需求概述**：

包含：需求名称、业务目标、需求类型（全新 / 扩展）、与已有能力的核心区别（若扩展）、后端影响面（涉及哪些 BC）、前端影响面（哪些页面）。

**下半部分——场景总览表**：

将需求拆为三类：

| 类型 | 含义 |
|------|------|
| **主流程** | 直接产生用户价值的端到端流程 |
| **支撑流程** | 为主流程提供能力、配置、或数据展示 |
| **异常流程** | 取消、失败、补偿、降级 |

为每条场景选择分析深度：

| 深度 | 后端适用场景 | 前端/交互适用场景 | 产出 |
|------|------------|-----------------|------|
| **L3 重** | 跨 BC、状态推进复杂、有补偿 | 复杂交互状态机、跨组件数据流、页面间副作用 | 后端：事件链 + 命令 + 策略 + 状态门禁；前端：交互流程 + 状态机 + 数据流向 + 组件边界 |
| **L2 中** | 有状态变化或数据依赖但不复杂 | 单页面内有数据流或组件边界设计 | 关键步骤 + 数据依赖 + 影响范围 |
| **L1 轻** | CRUD / 配置型 | 简单展示或表单，无复杂状态 | 操作描述 + 对主流程的影响边界 |

选择原则：主流程 → L3（必须），支撑流程 → L1/L2（按复杂度），异常流程 → 至少列出关键事件链。前端为主的需求，用前端维度判断深度。

**特别注意**：对照 `business-flows.md` 第二章 2.1「选品与决策」的数据依赖表，逐行检查是否有被需求影响但容易遗漏的场景（如详情页展示、购物车、结账页的数据依赖变化）。

**写完后**：告知用户第一章已写入，概述需求理解和场景盘点。如有需要用户选择的建模方向（如概念归属、拆分策略），附带一起提出。

---

### Step 2：写第二章「场景分析（事件流）」

**做什么**：按 Step 1 确定的深度，逐场景展开分析。分析过程中产生的设计决策**内联标注**在相关场景中（`> 决策 XXn：...`），不单独成章。

**以 `business-flows.md` 现有事件流为基线**，标注变化点（新增事件、修改触发条件、修改 payload），而非从白纸画起。

#### L3 重分析

按时间线展开，使用标准事件流表。必须覆盖：主成功路径 + 补偿/逆向路径 + 状态门禁。

> 事件流表格式详见 [`assets/overview-template.md`](./assets/overview-template.md)。

完成后做**数据可达性检查**：对涉及**决策、分支、类型判断、门禁**的步骤，验证所需数据在模型中是否可达（✅ 已有 / ❌ 缺失）。❌ 项驱动 Step 3 新增模型字段或概念。

#### L2 中分析

列出关键事件/状态变化 + 数据依赖；说清步骤与影响。**前端场景**：说明页面数据流向（从哪里取、传给哪个组件）、关键组件边界、与后端 API 的对接点。

#### L1 轻分析

自然语言描述操作步骤 + 对主流程的影响边界。

#### 查询影响

列出受影响的查询场景——数据组装方式变化、展示依赖变化等。

#### 流程间耦合

- 支撑流程的产出如何被主流程消费（实时引用 vs 快照）
- 支撑流程变更是否影响主流程的已有实例
- 异常流程是否需要跨流程补偿

**写完后**：告知用户第二章已写入，说明关键决策和数据缺口。有重大不确定问题则提出。

---

### Step 3：写第三章「变更分析」

**做什么**：将 Step 2 的横切分析转为纵切——按 BC 分组，写入每个 BC 的具体变更规格。横切按场景看全貌，纵切按 BC 落地到开发，两者互补。

**第三章是 Phase B 落地的唯一输入源**——必须详细到可以直接"抄写"到各 BC 文档，不是摘要。

每个 BC 包含（按需裁剪）：

| 子节 | 内容 | 对应 BC 文档 |
|------|------|-------------|
| **影响程度** | 🔴 重大 / 🟡 中等 / 🟢 轻微 / ⚪ 无变更 | — |
| **领域模型变更** | 新增/修改的聚合、实体、值对象（属性名、类型、约束）；不变式变更；状态机变更 | `domain-model.md` |
| **事件流变更** | 新增/修改的领域事件（名称、payload）；新增/修改的 API 端点；集成关系变更 | `event-flow.md` |
| **需求场景变更** | 新增的验收场景（Given/When/Then 要点）；修改的已有场景 | `requirements.md` |

**前端变更**单独成节（不归属任何 BC），与各 BC 子节并列：

| 子节 | 内容 | 落地目标 |
|------|------|---------|
| **影响程度** | 🔴 重大 / 🟡 中等 / 🟢 轻微 / ⚪ 无变更 | — |
| **新增/修改页面与组件** | 文件路径、功能职责、关键 props/emits | `ui-spec.md` |
| **数据流与状态** | composable 职责、响应式状态结构、inject/provide 链路 | 实现指引 |
| **界面规格（粗粒度）** | 布局描述（ASCII 图或文字），UI Spec 细节留给 `frontend-development` Skill 细化 | `ui-spec.md` |
| **手工验收 checklist** | 交互步骤 + 页面行为（替代 Gherkin，前端用手工验收） | 验收依据 |

前端变更节**只在需求有显著前端改动时写**；纯 CRUD 页面或简单展示可省略，在迭代计划的「前端变更」行说明即可。

**扩展型需求**：在每个 BC 的影响描述中，标注现有能力与本需求的关系（✅ 可复用 / 🔄 需调整 / 🔲 全新），融入变更描述而非单独成节。

末尾附 **BC 间数据流**，明确跨 BC 数据传递链。

关键检查：
- Step 2 中所有 ❌ 数据缺口在此步骤补齐为具体模型字段
- 场景分析中的每个 BC 影响在变更分析中有对应规格，反之亦然
- 跨 BC 事件 payload 发布方和消费方一致

**写完后**：告知用户第三章已写入，概述各 BC 影响程度与核心变更。有疑问则提出。

---

### Step 4：写第四章「迭代计划」+ 一致性检查

**做什么**：规划迭代、做一致性检查。

#### 迭代计划

将变更拆为可独立验收的迭代，明确依赖顺序。每个迭代标注：涉及 BC、前置依赖、后端变更、前端变更（粗粒度）、验收标准。引入新业务路径的迭代标注 **E2E 验收条件**（用例前缀 + 场景概述）。

#### 一致性检查

| 维度 | 检查项 |
|------|--------|
| 场景完整 | 所有场景已盘点？主流程做了 L3？支撑流程说明了影响边界？ |
| 事件完整 | L3 覆盖主成功路径 + 补偿路径？状态门禁无遗漏？ |
| 数据可达 | L3 数据依赖中所有 ❌ 在变更分析中已补齐？跨 BC 传递链完整？ |
| 场景↔变更 | 场景分析中的每个 BC 影响在变更分析中有对应规格，反之亦然 |
| 变更内部 | 需求场景有模型支撑；payload 与模型一致；不变式与状态机一致 |
| 前端 | 有显著前端改动时：变更分析中有「前端变更」节；界面规格粗粒度描述完整；手工验收 checklist 可独立执行 |
| 运营配置 | 需要手动录入的 Skill / 配置项是否已在迭代计划中列为独立工作项，含验收标准 |

若有不一致，回溯修正对应章节。

**写完后**：告知用户第四章已写入、Phase A 完成，请用户审阅完整 overview.md。用户确认后 Phase A 结束。

---

> **Phase A 到此结束。** overview.md 是自包含的需求方案，可长期独立存在。以下 Phase B 仅在用户明确指令时执行。

## Phase B：落地到各 BC

**触发条件**：用户明确说"落地到 BC"、"更新 BC 文档"、"准备开发"或类似指令。不可自动执行。

### 更新各 BC 问题域文档

以 overview 第三章「变更分析」为输入：

| BC 文档 | 操作 |
|---------|------|
| `requirements.md` | 新增/修改验收场景，标注 🔲/🔄 |
| `domain-model.md` | 新增/修改聚合、实体、值对象、不变式、状态机；更新 PlantUML 图 |
| `event-flow.md` | 新增/修改 API 契约、事件契约、集成关系 |

每处注明来源：`> 以下变更来自业务需求 [xxx](../../business-requirements/<name>/overview.md)`

### 更新系统文档

| 文档 | 更新内容 |
|------|---------|
| `docs/context-map.md` | BC 状态、集成关系 |
| `docs/business-flows.md` | 事件流、事件总表、路径枚举 |
| `docs/project-status.md` | BC 状态、路线图、决策记录、变更日志 |

### 跨文档一致性检查

| 维度 | 检查项 |
|------|--------|
| BC 内一致 | 场景有模型支撑；payload 与模型一致；图与表一致 |
| 跨 BC 一致 | 事件 payload 两侧一致；状态推进规则两侧一致 |
| 系统级一致 | context-map 与 BC 文档一致；business-flows 与各 event-flow 一致 |
| overview ↔ BC 一致 | 变更分析每条规格已落地，无遗漏无矛盾 |

## 衔接

**Phase A 后**：用户可审阅讨论、搁置调整、执行 Phase B、或直接调用 `deliver-requirement`。

**Phase B 后**：调用 `deliver-requirement` 按迭代计划编排执行，或单 BC 场景直接 `evolve-feature`。

## 关键约定

| 约定 | 说明 |
|------|------|
| 文档驱动 | 每步直接写入 overview.md，不在 chat 中做独立分析再"翻译"为文档 |
| 逐章确认 | 每章写完即是一次轻量确认，用户看到文档内容后自然反馈 |
| 决策内联 | 设计决策在场景分析中自然涌现，内联标注（`> 决策 XXn：...`），不单独成章 |
| Phase A 只写 overview | 不触碰 BC 文档和系统文档 |
| Phase B 需明确触发 | 用户明确说"落地"时才执行 |
| overview 自包含 | 变更分析必须详细到可直接落地 |
| 分级分析 | 主流程 L3，支撑流程 L1/L2，异常流程补关键事件链 |
| 只产出文档 | 分析阶段不修改代码、测试或域对象 |
