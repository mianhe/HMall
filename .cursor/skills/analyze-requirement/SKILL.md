# 分析业务需求

从一个**业务需求**出发，分析它对系统的影响，产出可执行的特性变更方案。

无论业务需求影响一个 BC 还是多个 BC，都走同一个流程。区别只是规模——影响面小时各步骤更轻量。

整体流程分为**两个阶段**：

- **Phase A（分析）**：理解需求 → 流程盘点 → 分级事件分析 → 领域建模 → 互动决策收敛 → 产出 overview.md → 一致性检查。**仅写 overview.md，不触碰任何 BC 文档和系统文档。**
- **Phase B（落地）**：用户明确指令后，将 overview 中的 BC 变更规格分发到各 BC 文档 + 更新系统文档 + 跨文档一致性检查。

各步骤可迭代。Phase A 完成后不自动进入 Phase B——分析完不一定马上开发，overview.md 可以长期作为独立的需求方案存在。

**核心原则：主价值流重事件，支撑流程轻流程，异常流程补关键事件链。**

> Skill 体系总览与流程链见 `.cursor/skills/README.md`。
> 业务流程全景（事件流、路径枚举）见 `docs/business-flows.md`。

## 何时用 / 不用

| 用 | 不用 |
|----|------|
| 新建 BC | 已知某 BC 的某个特性要调整 → `evolve-feature` |
| 已有 BC 引入新的领域概念或跨 BC 交互 | Bug 修复或场景微调 → `fix-bug-or-adjust-feature` |
| 一个业务需求需要多个 BC 同时演进 | |

**判断标准**：如果开发者能直接说出"改哪个 BC 的哪个 Feature"，就不需要本 Skill。本 Skill 解决的是"还不清楚要改什么、改哪些 BC"的分析问题。

## Step 0：理解需求与前置读取

### 0a. 明确业务需求

| 维度 | 要回答的问题 |
|------|------------|
| **需求名称** | 简短业务名称 |
| **业务目标** | 用户/业务想达成什么？ |
| **需求类型** | 全新需求 or 已有需求的扩展场景？若是扩展，标注关联的已有需求，并决定是新建 overview 还是在已有 overview 中新增迭代 |
| **后端影响面** | 可能涉及哪些 BC？哪些是核心变更、哪些仅需适配？ |
| **前端影响面** | 哪些前端页面需要新增或调整？（admin / web） |

### 0b. 前置读取与影响面初判

- `docs/context-map.md` 和 `docs/project-status.md`——了解系统结构与 BC 集成关系
- `docs/business-flows.md`——了解现有业务流程（事件流、路径枚举），评估新需求对流程的影响
- 所有可能受影响 BC 的已有文档（requirements.md、domain-model.md、event-flow.md）
- 关联 BC 的已有代码（Port 接口、事件消费者、状态枚举等）
- 可能受影响的前端界面规格（`docs/frontend/admin/ui-spec.md`、`docs/frontend/web/ui-spec.md`）——了解现有页面结构，判断哪些页面需要调整

**影响面初判**：读完 `business-flows.md` 后，按其 §五「与需求分析的衔接」逐一回答 5 个检查问题（影响哪段、影响哪些事件、新增路径还是影响现有、是否打破 N2O ⊥ O2F、测试覆盖是否完整）。用此结果校正 0a 中的"后端影响面"，避免遗漏。

**复用初判**：对每个受影响 BC，标注其现有能力与本需求的关系（✅ 可直接复用 / 🔄 需调整 / 🔲 全新）。复用程度决定分析轻重——复用越多，分析越聚焦于增量部分。

## 交互式确认

需要用户确认时，**必须使用 AskQuestion 工具**，让用户通过选择完成确认。

### 原则：只问用户该决定的事

- **要问**：有多个合理方案的业务取舍、Agent 无法自行判断的歧义点、需要用户拍板的设计决策。
- **不问**：技术正确性验证（事件链是否完整、聚合边界是否合理、属性类型是否准确）——这些是 Agent 的职责，做错了用户自然会纠正。
- **不逐项确认**：不要把「完整性」「分类」「深度」等维度拆成独立问题去问。

### 使用规范

- 用 `AskQuestion` 的 `options` 提供选项，附简短说明。多选时设 `allow_multiple: true`。
- 需要自由文本时增加「其他（请在下次回复中说明）」兜底选项。
- 一次调用可包含多个 `questions`，减少交互轮次。

### 确认点（仅 2 个）

| 确认点 | 时机 | 问什么 |
|--------|------|--------|
| **① 流程盘点** | Step 1 后 | 展示流程清单，问「有没有遗漏的流程」+ 附带需要用户选择的建模方向（如有） |
| **② 设计决策** | Step 2-3 完成后，进入 Step 4 | 将分析中发现的所有需用户拍板的决策点一次性收集 |

Step 2-3 完成后不单独停下来确认。overview 写完后不做最终确认——用户审阅后有问题自然会说。

## Step 1：流程盘点（Flow Inventory）

**目标**：在深入分析前，先把需求涉及的所有业务流程列出来、分好层，避免遗漏隐性流程（如后台配置、异常补偿）。

### 1a. 识别并列出流程

将需求拆为三类流程：

| 流程类型 | 含义 | 典型例子 |
|----------|------|---------|
| **主流程** | 直接产生用户价值的端到端流程 | 带定制内容的下单→支付→履约→签收 |
| **支撑流程** | 为主流程提供能力或配置的流程 | Admin 配置可选项、维护规则 |
| **异常流程** | 主流程的取消、失败、补偿、降级 | 支付超时取消、生产失败重试 |

每条流程用一句话描述：`谁 → 做什么 → 产生什么业务结果`。

### 1b. 为每条流程选择分析深度

| 深度 | 代号 | 适用场景 | 分析方式 | 产出 |
|------|------|----------|----------|------|
| **重分析** | L3 | 跨 BC、状态推进复杂、有补偿 | 完整事件驱动分析（Event → Command → Policy） | 事件链 + 命令 + 策略 + 状态门禁 + 验证映射 |
| **中分析** | L2 | 有少量状态变化但不复杂 | 关键事件 + 状态变化 | 事件清单 + 影响 BC + 验证点 |
| **轻分析** | L1 | CRUD 型、配置型、无显著状态流转 | 流程步骤 + 影响边界 | 操作描述 + 对主流程的影响规则 |

**选择原则**：
- 主流程（交易、履约等跨 BC 编排）→ **L3**（必须）
- 支撑流程（配置管理、规则维护）→ **L1 或 L2**（按复杂度）
- 异常流程 → 跟随其所属主流程的深度，至少列出关键事件链

**产出**：流程清单表（流程名 + 类型 + 分析深度 + 一句话描述）。

### ✅ 确认点 ①：流程盘点

展示流程清单表后，用 **AskQuestion** 问一个简洁问题：「流程清单是否有遗漏？」（选项：完整 / 有遗漏请补充）。如果分析中发现需要用户选择的建模方向（如「新概念用哪种方式融入已有模型」），附带一起问。

不要逐项确认分类和分析深度——这些是 Agent 的判断。用户有异议会主动说。

## Step 2：分级事件分析

**目标**：按 Step 1 确定的深度，逐条流程做事件分析。先看"发生了什么事"（Event），再追"谁触发了什么操作"（Command），最后补"系统自动规则"（Policy）。

**以 `business-flows.md` 现有事件流为基线**，标注变化点（新增事件、修改触发条件、修改 payload），而非从白纸画起。

### 2a. L3 重分析：完整事件驱动（主流程）

按时间线逐步展开，使用标准事件流表（`# | Event 🟧 | Command ⌘ | Policy/Rule ⟳ | BC | 影响识别`）。

> 各列含义与格式详见 [`assets/overview-template.md`](./assets/overview-template.md) 的"事件流表列说明"。

**BC 列仅标事件的归属方（发布者）**，不标消费方向——消费方的反应写在 Policy 列。主成功路径和补偿路径分别建表，补偿路径表最后一列改为"与现有差异"。

**必须覆盖**：
- 主成功路径（happy path）的完整事件链
- 补偿/逆向路径的事件链
- 状态门禁（某事件是另一事件的前置条件）

### 2b. L2 中分析：关键事件清单

列出该流程涉及的关键事件和状态变化：

- 事件名 + 触发条件 + 影响的 BC
- 不需要逐步展开 Command/Policy，但需标注"对主流程的影响点"

### 2c. L1 轻分析：流程步骤与影响边界

用自然语言描述操作步骤，重点说清楚：

- 谁做什么操作（Admin/系统/定时任务）
- 操作结果影响什么（哪些数据、哪些可选项）
- **对主流程的影响边界**——这是 L1 最关键的产出，例如：
  - "配置变更仅影响新订单的可选项，不影响历史订单快照"
  - "规则变更即时生效 vs 需要发布"

可选：列出审计/追踪事件（如 `XxxEnabled`、`XxxDisabled`），不强求。

### 2d. 查询影响分析

除事件/命令（写路径）外，列出受影响的**查询场景**——例如：数据组装方式变化、唯一键语义变化导致的查询逻辑调整。查询影响容易被遗漏，但往往是 bug 的来源。

### 2e. 流程间耦合分析

分析支撑流程与主流程的连接点：
- 支撑流程的产出如何被主流程消费（实时引用 vs 快照）
- 支撑流程的变更是否影响主流程的已有实例
- 异常流程是否需要跨流程补偿

**产出**：每条流程的事件分析（按深度裁剪）+ 流程间耦合关系 + 查询影响清单。

Step 2 完成后**不停下来单独确认**——直接进入 Step 3。分析中发现的待决策点（如「某概念归哪个 BC」「某交互同步还是异步」）记录下来，留到 Step 4 一起问。

---

## Step 3：领域建模

**目标**：识别聚合、实体、值对象，明确事件与领域对象的归属关系。

- 为每个事件追问：「这件事发生在哪个业务对象上？」
- 识别聚合根、子对象，将事件归类到对应聚合
- 按 BC 分组输出各 BC 的模型变更（新增/修改的聚合、实体、属性），标注 BC 间的新增关联
- **不变式变更**：显式列出每个受影响聚合的不变式变化（唯一性约束、取值范围、状态转换规则等）。包括**业务前置条件**——某些场景要求特定业务状态已达成才能执行（如"商品已交付才能补购"），这些条件会成为新的不变式
- 建模过程中会反哺事件流——发现缺失事件、合并或拆分事件

**产出**：领域模型图、事件清单（含所属聚合）、各聚合的状态/生命周期、不变式变更清单。

Step 3 完成后**不停下来单独确认**——直接进入 Step 4。建模中发现的待决策点同样记录下来，在 Step 4 一并收集。

---

## Step 4：互动决策收敛

**目标**：逐一澄清关键设计决策。必须与用户讨论确认，不可自行假设。

### 4a. 通用决策维度

| 维度 | 要回答的问题 |
|------|------------|
| **同步 vs 异步** | 每个跨 BC 交互是同步调用还是事件驱动？ |
| **职责归属** | 某个业务逻辑由哪个 BC 负责？ |
| **查询编排** | 跨 BC 数据组合由谁负责？前端编排 / BFF 聚合 / BC 聚合 API？ |
| **状态推进规则** | 下游多实例状态不同步时，上游如何推进？ |
| **取消/补偿边界** | 什么状态下允许取消？补偿步骤是什么？ |
| **数据归属与快照** | 跨 BC 数据是快照还是引用？ |
| **建模方式** | 新概念如何融入已有模型？ |
| **MVP 范围** | 哪些能力先简化？ |

### 4b. 必问决策清单

以下决策在大多数需求中都需要明确回答。事件分析过程中若已自然覆盖则标注"已确认"，否则必须主动提问：

| 决策项 | 说明 |
|--------|------|
| **冻结点** | 用户提交的内容在何时成为不可变快照？（下单时 / 支付时 / 履约前） |
| **配置变更影响范围** | 后台配置变更是否影响已有实例？（快照优先 vs 实时引用） |
| **取消与补偿边界** | 各状态下取消是否允许？补偿步骤是什么？ |
| **数量语义** | 批量场景下，定制内容按整批统一还是逐件独立？ |
| **内容治理等级** | 用户输入内容的校验级别？（基础校验 / 敏感词 / 人工审核） |
| **生效范围** | 新能力按全局生效还是按特定对象绑定？ |

### ✅ 确认点 ②：设计决策

将 Step 2-3 分析中积累的待决策点 + 4b 必问清单中尚未覆盖的项，**用一次 AskQuestion 调用一次性收集**。

- 每个决策作为一个 `question`，提供选项 + 简短说明
- 已在分析过程中自然确定的决策标注「已确认」，不再重复问
- 用户回答后记录为 `{编号} | {决策} | {说明}`
- 决策可能反过来修改事件流和领域模型——这是正常的迭代

## Step 5：产出 overview.md（Phase A 产出）

Phase A 的唯一产出是 `docs/business-requirements/<name>/overview.md`。**不修改任何 BC 文档和系统文档**——overview 必须自包含，作为独立的需求方案长期可读。

> **编写 overview 前必须先读取 [`assets/overview-template.md`](./assets/overview-template.md)**——其中定义了完整的章节结构（§一～§五）、事件流表格式、§四 各 BC 变更规格的子节定义与示例、迭代计划规范。

**各 Step 产出 → overview 章节的映射**：

| 分析步骤产出 | 写入 overview 章节 |
|-------------|-------------------|
| Step 0 需求理解 | §一 背景与目标 |
| Step 1 流程清单 | §二 场景总览表 |
| Step 2 事件分析 | §二 各场景展开（事件流表、查询影响等） |
| Step 3 领域建模 | §四 各 BC 的领域模型变更子节 |
| Step 2 + 3 综合 | §四 各 BC 的事件流变更、需求场景变更子节 |
| Step 4 设计决策 | §三 设计决策表 |

**关键约束**：
- **§四 是 Phase B 的唯一输入源**——必须详细到可直接"抄写"到各 BC 文档，不是摘要
- §二（跨 BC 横切）与 §四（单 BC 纵切）互补、不重复

## Step 6：一致性检查（Phase A）

Phase A 的一致性检查范围限于 **overview.md 内部**——因为此时还没有修改 BC 文档和系统文档。

| 检查维度 | 具体检查项 |
|----------|-----------|
| **流程完整** | 是否所有流程都已盘点？主流程是否都做了 L3 事件分析？支撑流程是否说明了对主流程的影响边界？ |
| **事件完整** | 每条 L3 流程是否覆盖了主成功路径 + 补偿路径？是否有状态门禁遗漏？ |
| **§二 ↔ §四 一致** | §二 事件流中提到的每个 BC 影响，在 §四 中都有对应的变更规格；反之亦然 |
| **§四 BC 内一致** | 每个 BC 的需求场景都有领域模型支撑；事件 payload 与领域模型属性一致；不变式变更与状态机一致 |
| **§四 跨 BC 一致** | 事件 payload 在发布方和消费方的描述一致；BC 间数据流的源字段和目标字段对应正确 |
| **§三 ↔ §四 一致** | 设计决策与各 BC 变更规格不矛盾 |
| **前端影响已标注** | 迭代计划的每个迭代都标注了受影响的前端页面和变更要点 |
| **分析适度** | 是否存在"重流程漏做事件分析"或"轻流程过度建模"？ |

> Phase B 执行时有独立的跨文档一致性检查（见 Step 7c）。

一致性检查完成后，overview.md 即为 Phase A 最终产出。**不做额外的最终确认**——用户审阅 overview 后有问题自然会反馈。

---

> **Phase A 到此结束。** overview.md 已是自包含的需求方案，可以长期独立存在。以下 Step 7 仅在用户明确指令时执行。

## Step 7：落地到各 BC（Phase B）

**触发条件**：用户明确说"落地到 BC"、"更新 BC 文档"、"准备开发"或类似指令。**不可在 Phase A 结束后自动执行。**

Phase B 将 overview.md §四 的变更规格分发到各 BC 文档和系统文档。

### 7a. 更新各 BC 问题域文档

以 overview.md §四 为输入，对每个受影响 BC 的文档做增量修改：

| BC 文档 | 输入源（overview §四 子节） | 操作 |
|---------|-----------------------|------|
| `requirements.md` | 需求场景变更 | 新增/修改验收场景，标注 🔲/🔄 |
| `domain-model.md` | 领域模型变更 | 新增/修改聚合、实体、值对象、不变式、状态机；更新 PlantUML 图和属性表 |
| `event-flow.md` | 事件流变更 | 新增/修改 API 契约、事件契约、集成关系 |

每处变更注明来源：`> 以下变更来自业务需求 [xxx](../../business-requirements/<name>/overview.md)`

### 7b. 更新系统文档

| 文档 | 更新内容 |
|------|---------|
| `docs/context-map.md` | 上下文说明表（BC 状态）、集成关系表 |
| `docs/business-flows.md` | 事件流（§二）、事件总表（§三）、路径枚举与测试覆盖（§四） |
| `docs/project-status.md` | BC 状态表、路线图、决策记录、变更日志 |

### 7c. 跨文档一致性检查

| 检查维度 | 具体检查项 |
|----------|-----------|
| **BC 内一致** | 每个 scenario 都有领域模型支撑；事件 payload 与领域模型一致；模型图与属性表一致 |
| **跨 BC 一致** | 事件 payload 两侧 BC 文档一致；状态推进规则两侧一致 |
| **系统级一致** | context-map 集成关系与各 BC 文档一致；business-flows 事件总表与各 BC 的 event-flow 一致；project-status 状态正确 |
| **overview ↔ BC 一致** | overview §四 的每条变更规格都已落地到对应 BC 文档，无遗漏、无矛盾 |

## ⚠️ 衔接

**Phase A 完成后**：overview.md 可以长期存在。用户可以：
- 审阅方案、与团队讨论、搁置或调整——不影响现有 BC 文档
- 随时回来执行 Phase B 落地
- 直接调用 `deliver-requirement` 开始交付（`deliver-requirement` 会在需要时触发 Phase B）

**Phase B 完成后**：各 BC 文档已更新，可以：
- 调用 `deliver-requirement` 按迭代计划编排各 Skill 执行
- 单 BC 场景可直接执行 `evolve-feature`

**禁止在分析对话中直接修改代码、测试或域对象。** 分析阶段只产出文档，实现阶段必须切换到对应 Skill。

## 关键约定

| 约定 | 说明 |
|------|------|
| **Phase A 只写 overview** | Phase A 不触碰 BC 文档和系统文档——分析完不一定开发，overview 可独立存在 |
| **Phase B 需明确触发** | 只有用户明确说"落地到 BC"时才执行 Phase B，不可自动进入 |
| **overview 自包含** | overview.md 是完整的需求方案：§四 的 BC 变更规格必须详细到可直接落地，而非摘要 |
| **流程先行** | 分析从流程盘点入手，先看全貌再逐条深入，避免遗漏隐性流程 |
| **分级分析** | 主价值流重事件，支撑流程轻流程，异常流程补关键事件链——不对所有流程做同等深度分析 |
| **事件驱动** | L3 流程的分析骨架：先 Event（发生了什么）→ 再 Command（谁做了什么）→ 再 Policy（自动规则）→ 自然得出 Impact（改什么、怎么验） |
| **事件归属不标方向** | 事件表 BC 列仅标发布者，不标消费者方向——事件是已发生的事实，消费方的反应写在 Policy 列 |
| **场景总览先行** | §二 先用一张总览表展示所有场景全貌，再逐一展开——读者一眼看到全景、按需深入 |
| **轻量确认** | 仅 2 个确认点：① Step 1 后问流程有无遗漏 ② Step 4 一次性收集设计决策。Step 2-3 不单独停下确认，overview 写完不做最终确认。技术正确性是 Agent 的职责，不问用户。 |
| **互动收敛** | 确认点必须使用 **AskQuestion 工具**（见 §交互式确认），只问用户需要做选择的事，不做逐项验证式确认 |
| **迭代精化** | 各步骤可多次往返，逐步收敛；事件分析、领域建模、决策三者互相反哺 |
| **决策先于实现** | 设计决策与用户确认后再编写特性，避免返工 |
| **前端影响前置识别** | 分析阶段即标注每个迭代的前端影响面（哪些页面、做什么），为 `deliver-requirement` 编排前端工作提供输入 |
| **分析只产出文档，不产出代码** | 分析阶段的产出是文档变更，代码实现必须通过 `evolve-feature` 等 Skill 执行 |
